# Контейнерные окружения: решения и бэклог

Поведение для пользователя описано в [Docker](docker.md) и [интеграциях](integrations.md); здесь — почему сделано так, что сознательно не реализовано и какие правила соблюдать при развитии. Документ сверен с версией 0.4.1.

## Сценарий

`gh:/owner/repository` → просмотр без загрузки → окно клонирования (папка, образ, сеть, порты) → фоновая задача: образ, clone → обычный workspace `/projects/...` → установка зависимостей и запуск вручную из терминала. Установка зависимостей и запуск кода при клонировании автоматически не выполняются. Локальные проекты сохраняют свой способ запуска. Окружение хранится в `Project.environment` (`projects.json`): Docker context, image, network, ports.

## Принятые решения

### Ограниченный `docker run` вместо автоматического Dev Container CLI

Режим по умолчанию — управляемый `docker run` с параметрами, которые формирует Projector. Репозиторные `devcontainer.json`, Dockerfile, Features, Compose, mounts и lifecycle hooks сами по себе не исполняются: иначе репозиторий мог бы отменить ограничения. Исполнение возможно только после явного доверия пользователя (`@devcontainers/cli`, один образ, один конфиг на проект; детали — [Docker](docker.md#доверие-к-репозиторию-и-dev-container)). Не передавайте репозиторную конфигурацию движку без проверки всех исполняющих стадий и не называйте ограниченный режим реализацией стандарта Dev Containers.

### Checkout на хосте, отдельные временные контейнеры

Файлы лежат в папке, выбранной пользователем, и монтируются в `/workspace`; служебного каталога `$XDG_DATA_HOME/projector/workspaces` нет. Дерево, редактор и поиск работают с хостовым backend. Rootfs, HOME и `/tmp` контейнера не являются хранилищем проекта; терминалы делят файлы, но не процессы. Named volumes потребуют отдельного filesystem provider: API не должен читать `/var/lib/docker/volumes` напрямую. Удалённый Docker вне scope: допускаются локальные contexts с Unix socket.

### Явная сеть и отсутствие host fallback

Для clone сеть временно включается (HTTPS), для выполнения по умолчанию `none`; `bridge` открывает интернет и LAN. Порты публикуются только на `127.0.0.1`. Нет Docker socket, host HOME и переноса настроек/секретов хоста. Git изолированного checkout и Bash агента тоже выполняются в Docker (hooks Git отключены), сменить cwd на хост нельзя. Отказ Docker никогда не приводит к запуску команды на хосте. Docker разделяет ядро хоста, поэтому абсолютная безопасность против заведомо вредоносного кода не обещается; дисковых квот и суммарного лимита нескольких контейнеров нет.

### Жизненный цикл

Контейнер принадлежит PTY-сессии или вызову инструмента и удаляется вместе с ними; штатный выход сервера удаляет принадлежащие ему контейнеры. После SIGKILL интерактивные терминалы закрываются сами, а неинтерактивные запуски убирает очистка при следующем старте по меткам `io.projector.environment` и `io.projector.server` (pid и время запуска владельца): чужие контейнеры и контейнеры живого Projector не затрагиваются.

## Проверки

`vp run test:docker` — fixture CLI без daemon, входит в `vp run check`. `vp run test:live` — настоящий Docker (изоляция, порты, очистка, SIGKILL, Dev Container), в `check` не входит. Не проверялись live: private Docker clone, реальный OAuth Device Flow, установка AI CLI, Dev Container с Features и Compose; холодный/тёплый запуск и размеры кешей не измерялись.

## Не реализовано

| Работа                                                                                           | Критерий готовности                                                                                                               |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| Настройки окружения готового проекта (image/network/ports, проверка программ)                    | Изменение завершает затронутые сессии; UI и агент видят одни параметры; сеть включается явно. Сейчас окружение задаётся при клоне |
| IDE-команды статуса, перенастройки, пересборки, экспорта окружения; отмена подготовки не из окна | Команды с понятными `title`/`description`, как у остальных (`ide.environment.port.open` — единственная)                           |
| Шаблоны JS/TS, Python, универсального Linux; lockfiles, `packageManager`, выбранная подпапка     | Подготовка зависимостей запускается явно; нестандартный проект получает терминал и понятную причину неполной подготовки           |
| AI CLI и адресная авторизация внутри окружения                                                   | Полномочия не передаются через весь HOME; scope и срок жизни секретов понятны пользователю                                        |
| Clone выбранного ref/commit, независимые эксперименты                                            | Ref/commit и источник сохраняются в модели; отдельные checkout не делят writable файлы                                            |
| Сопоставление путей и drop файлов в Docker-терминалах (ограниченный режим)                       | Контейнерные пути разрешаются только в checkout; загрузка, symlinks и cleanup проверены реально                                   |
| Политика Dev Containers, Features, Compose в доверенном режиме                                   | Валидация конфигурации, mounts, runArgs, lifecycle и секретов до выполнения; неподдерживаемое даёт понятный отказ                 |
| Многосервисные проекты в рамках политики ограничений                                             | Live-сценарий с БД/Redis; ограничения сохраняются и для вспомогательных сервисов                                                  |
| Перенос ключей провайдеров из `providers.json` в хранилище секретов ОС                           | Токены интеграций уже в хранилище; `providers.json` пока хранит ключи в файле                                                     |
| Общий OAuth App Projector, поиск GitHub, write-сценарии                                          | Вход без пользовательского Client ID; дополнительные полномочия объяснены отдельно от просмотра/клонирования                      |
| Байтовый прогресс клонирования и pull                                                            | Сейчас только фазы: проверка → pull → clone → добавление                                                                          |

## Правила будущего экспорта

Копирование и переход в host-режим — разные операции. Сохраняйте `.git`, tracked/untracked изменения, dotfiles и пользовательские файлы. Исключения для зависимостей и generated files задавайте явно; не выбрасывайте все gitignored данные. Rootfs, процессы и данные дополнительных volumes не часть checkout; для БД нужен отдельный backup/export.

Публикуйте временную копию на целевой файловой системе с отказом при коллизии; неявного merge с существующей папкой нет. При ошибке исходные файлы и окружение остаются доступными, удаление источника — отдельное действие после успешного экспорта. Переход в host-режим требует остановки сессий и явного изменения профиля выполнения; host toolchain не считается установленным.
