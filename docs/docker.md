# Docker

[Интеграции](integrations.md) · [IDE-команды](ide-commands.md)

В настройках интеграций включите Docker и выберите локальный context. Нужны установленный Docker CLI, доступ к daemon и, для Compose-действий, плагин `docker compose`. Projector не меняет глобальный Docker context и не запускает daemon автоматически. Удалённые SSH/TCP contexts пока недоступны.

В боковой панели проекта кнопка Docker показывает связанные сервисы. «Открыть» открывает обычную вкладку Docker: её можно закрыть, переместить, разделить и восстановить вместе с workspace. «Все контейнеры» показывает контейнеры выбранного context, включая не связанные с текущим проектом. Действия в этом режиме относятся к выбранному контейнеру.

## Изолированное клонирование GitHub

Окно клонирования по умолчанию предлагает Docker, образ `node:24-bookworm` и выключенную сеть для запуска. Можно выбрать другой доверенный образ с Bash и Git либо явно выбрать локальный запуск. Нужен работающий локальный Docker daemon; включать отдельную панель Docker необязательно. При отсутствии образа Projector скачивает его до клонирования. Ошибка Docker не переключает проект на запуск на хосте.

Сам `git clone` выполняется в ограниченном контейнере с временно включённой сетью для HTTPS. GitHub token передаётся только этому контейнеру через временный файл с правами `0600`, который удаляется после операции. В последующие терминалы token не попадает. После успеха открывается обычный `/projects/...`, а профиль Docker сохраняется в каталоге проектов на диске.

Shell, команды проекта, Git и Bash штатного агента выполняются внутри Docker. Codex, Claude Code и OpenCode также запускаются внутри выбранного образа: их нужно установить там самостоятельно, авторизация хоста не переносится. Каждый терминал и вызов инструмента получает отдельный контейнер с общей папкой проекта `/workspace`. Файлы и установленные в ней зависимости сохраняются, `/tmp` и домашняя папка контейнера временные. В образах с Corepack доступны его обёртки pnpm/yarn; установка зависимостей требует явно разрешённой сети.

Контейнер работает с UID/GID пользователя, без root, дополнительных capabilities, повышения привилегий, домашней папки хоста и Docker socket. Корневая файловая система доступна только для чтения. Лимиты на контейнер: 2 CPU, 2 GiB памяти без дополнительного swap и 256 процессов. Единственный bind mount — папка проекта; права записи в ней сохраняются. Остановка или закрытие терминала удаляет его контейнер вместе с процессами; штатное завершение Projector также удаляет принадлежащие ему контейнеры.

Сеть по умолчанию `none`. Флажок в окне включает `bridge`: это разрешает интернет **и доступ к локальной сети**, а не только реестры пакетов. До пяти выбранных TCP-портов публикуются на случайных портах **127.0.0.1**. Терминал показывает ссылки на них через `ide.environment.port.open`; runner сопоставляет адрес dev-сервера с опубликованным портом. Сервер приложения должен слушать `0.0.0.0` внутри контейнера.

Это управляемое окружение для разработки, а не полная реализация спецификации Dev Containers. Конфигурация репозитория `devcontainer.json`, Dockerfile, Compose, Features, mounts и lifecycle hooks автоматически не выполняется: иначе репозиторий мог бы отменить ограничения. Проект с такими требованиями нужно адаптировать к доверенному образу. Произвольные Docker/Compose-действия в изолированном проекте запрещены.

Docker использует ядро хоста, поэтому такая изоляция не заменяет виртуальную машину для заведомо вредоносного кода. Дисковая квота папки проекта и общий лимит для нескольких одновременно запущенных контейнеров не установлены. Файловые ссылки и загрузка файлов через терминал пока имеют те же ограничения, что и другие Docker-терминалы.

## Compose

Projector обнаруживает `compose.yaml`, `compose.yml`, `docker-compose.yaml`, `docker-compose.yml` в корне проекта. Сохраните явную привязку: context, Compose project name, упорядоченный список файлов, profiles и env-файлы. Пути файлов задаются относительно проекта; выход за его границы, включая symlinks, запрещён. Содержимое env-файлов не возвращается в браузер.

Привязка не запускает код. «Поднять» выполняет `compose up -d`; доступны stop, restart, build, pull и down. Сборка и запуск используют конфигурацию проекта, включая предусмотренные ею команды и mounts. Projector не превращает произвольную Compose-конфигурацию в ограниченную песочницу.

«Остановить» сохраняет контейнеры. «Удалить окружение» требует подтверждения, останавливает и удаляет контейнеры и сети; Projector не передаёт `--volumes`. Volumes остаются. Параллельные Compose-операции одного имени в одном context блокируются, включая операции из разных открытых проектов.

## Контейнеры и терминалы

Список показывает состояние процесса отдельно от healthcheck, exit code завершившегося контейнера, образ и опубликованные порты. Подробности содержат mounts и время запуска. Статус обновляется каждые пять секунд на видимой странице; после ошибки подключение проверяется снова. CPU/RAM, управление images/volumes/networks и поток Engine events пока не реализованы.

Start, stop, restart, remove, поток логов и shell используют существующие PTY-сессии и вкладки терминала. Операция возвращает сессию сразу; успех определяется её `status` и `exitCode`, а не ответом HTTP 201. Логи начинаются с последних 200 строк с timestamps и продолжаются в потоке. Терминальная история и reconnect используют штатный xterm backend. Повторяйте Docker-действие из панели Docker; обычный restart терминала не подменяет его shell хоста.

Shell выполняет `docker exec -it` с `sh` или `bash`. Resize, ввод и reconnect идут через существующий PTY. Выход из shell командой `exit` завершает оболочку. Закрытие/остановка Docker-клиента и перезапуск Projector не останавливают контейнер и не гарантируют завершения задач, запущенных через exec. Для остановки всего workload используйте stop контейнера.

Файловые ссылки и drag-and-drop путей хоста в Docker-терминалах отключены до реализации сопоставления host/container. Веб-ссылки работают. Опубликованный TCP-порт можно открыть явно как HTTP или HTTPS; наличие порта не означает, что на нём работает веб-сервис.

## Хранение и команды

Настройки и привязки сохраняются через существующий integration store в `$XDG_DATA_HOME/projector/integrations.json`, атомарно и с правами `0600`. Секретные переменные контейнеров не включаются в публичный snapshot. Настройки и workspace не используют browser storage.

В scope `docker:<projectId>` зарегистрированы `ide.docker.open`, `.sidebar.open`, `.status`, `.refresh`, `.context.select`, `.container.select`, `.binding.save`, `.logs.read`, `.port.open` и команды действий: `.start`, `.stop`, `.restart`, `.remove`, `.logs`, `.shell`, `.up`, `.composeStop`, `.composeRestart`, `.down`, `.build`, `.pull`. Передавайте полный `containerId`; Compose-команды принимают необязательный `service`. Удаление через SDK требует `confirm: true` либо интерактивного подтверждения. Scope `docker:settings` предоставляет `.settings.status` и `.settings.save` на странице настроек.

Проверка транспорта, сохранения, границ файлов, contexts, ошибок daemon, подтверждений, параллельных операций и реального PTY с fixture CLI: `vp run test:docker`. Эта проверка не требует настоящего daemon. Она включена в `vp run check`.
