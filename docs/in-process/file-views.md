# Файловые представления: снимки, коммиты и сравнения

Рабочий документ: открытые решения и план. Текущее устройство — [architecture.md](../architecture.md) («Профили workspace»), [usage.md](../usage.md) («Файлы и поиск»), [ide-commands.md](../ide-commands.md). Здесь не дублируются контракты, которые уже описаны.

## Задача

Панель файлов показывает рабочую копию проекта. Нужен универсальный способ читать файловые представления из разных мест:

- дерево на произвольном коммите;
- сравнение двух снимков (ревизий; позже — других источников);
- в перспективе — индекс, контейнер, том.

Сначала — контракт и read-only деревья, затем сравнение.

## Что уже сделано

- `FileScope` и чистые функции ключа, параметров, заголовка и подписи (`core/modules/workspace/scope.ts`).
- `workspaceScopeRequest` добавляет параметры снимка к обычному действию `tree`/`file`; вызовы больше не передают `rev` вручную.
- `FileTree` принимает `scope` и готовые `decorations`, а не `rev`, `readonly` и `gitChanges`. Запись, DnD и импорт проверяют вид снимка через `isLiveScope`.
- Дерево коммита стало общим разделом `tree` с параметром `scope` (`ScopeTreeSection`). Отдельный вид `commit-tree` и специальные ветки в `ProjectWorkspace`/`sidebar-views` убраны; заголовок и подпись источника выводятся из scope.
- `OpenFile.scope` заменил `OpenFile.rev`; ключ вкладки собирает `fileTabKey`. Live-ключи (`path:file`, `path:index`, `path:working`, `external:...`) сохранены, чтобы старые сессии открывались. Схема сессии понимает и новый `scope`, и старый `rev`.
- Возможность профиля `snapshots` заменила `historyTree`. Локальный профиль читает `tree`/`file` с `rev`; GitHub и GitLab читают дерево и файлы по произвольному sha и кешируют каталоги по снимку (`sha:path`), а не по изменяемому `metadata`.
- Статусы Git, коммитов и merge request сведены к `FileChange` (`kind`: added, modified, deleted, renamed, copied, conflict). `fileChangeDecorations` строит пометки дерева, `ScopeTreeSection` и панель изменений MR используют одну нормализацию.
- Сравнение локальных и удалённых снимков подключено: `changes?from&to` и `compare-file?from&to&path&originalPath`, общий `ChangesTree` для панели MR и нового раздела `changes`, вход из обзора коммита (`ide.git.commit.openChanges`, первый родитель → коммит). `FileScope.compare` открывает diff-вкладки с двумя сторонами, подписи — короткие хеши. GitHub использует compare API (лимит 300 файлов), GitLab — `repository/compare`; обе стороны файла читаются по ref.
- Временные разделы и их read-only-вкладки сохраняются в сессии: scope сериализуется, раздел восстанавливается из параметров, вкладки снимка — только вместе со своим разделом.
- Вложения снимка: `workspaceScopeAssetUrl`, локальный `asset?rev`, GitHub `asset?commit`, GitLab `asset?sha`; растровые изображения и SVG из коммита открываются своими просмотрщиками, Markdown рендерится с картинками и ссылками того же снимка.
- Поиск по коммиту: локальный `search?rev` через `git grep` и GitLab `search?rev` через поиск по blobs с `ref`; отдельный раздел `search-scope` с тем же `SearchPanel`, переход из результата открывает файл в том же снимке. GitHub поиск по произвольному коммиту не объявляет: его code search API читает только ветку по умолчанию.
- Серверные и браузерные тесты дерева, `FileScope`, удалённого чтения по коммиту, сравнения снимков и группировки разделов.

## Текущие границы

- Панель MR остаётся на `pull-files`, но уже приводит файлы к общему `FileChange` через `pullRequestFilesToFileChanges` и рисует их тем же `ChangesTree`, что и сравнение снимков. Переход на compare scope не нужен: у merge request есть `diffRefs`, но локальная копия GitHub-проекта может не знать удалённые хеши, а GitLab compare теряет часть MR-метаданных. Это адаптер, а не эвристика по записи проекта.
- HTML, `siteUrl` и архивы на снимке явно не поддерживаются: HTML открывается как код, архив — как обычный файл без распаковки, `siteUrl` остаётся только для live; вкладка показывает подпись с причиной. Compare-снимок остаётся текстовым diff без Markdown-рендера и картинок.
- Поиск по удалённому снимку сделан для GitLab; GitHub его не объявляет: `/search/code` не принимает коммит. Локальный и GitLab-поиск включаются из одного раздела `search-scope`.
- Полного union-дерева с неизменёнными и удалёнными узлами нет. Для сравнения выбран список изменённых файлов.

## Контракт

```ts
export type FileScope =
  | { kind: "live" }
  | { kind: "commit"; rev: string }
  | { kind: "compare"; from: string; to: string };
```

- `rev`/`from`/`to` — конкретные хеши, а не имена веток. Ветка резолвится в хеш при открытии.
- Ключ для вкладок, сессий и кешей: `live`, `commit:<hash>`, `compare:<a>..<b>`.
- `FileScope` — данные: без методов, провайдеров и путей на диске.
- Чтение: `workspaceScopeRequest(projectId, scope, action, params)`. Действие остаётся `tree` или `file`, scope добавляет только `rev`/`from`/`to`.
- Права не образуют вторую матрицу: `editable = scope.kind === "live" && capabilities.write`, `watchable = scope.kind === "live" && capabilities.watch`. Поиск остаётся возможностью провайдера: scope добавляет `rev`, а источник решает, умеет ли он искать по снимку.
- Идентичность `(scope, path)` нужна только вкладкам, сессиям и кешам. Внутри одной панели путь уникален; selection и reveal остаются путевыми.

## Решения

- **Без фасада `FileSource`.** Он дублировал бы `FilesProvider` и требовал нового слоя в каждом адаптере. Хватает `FileScope` и функций чтения.
- **Без `FileSourceCapabilities`.** Права выводятся из вида снимка; отдельная матрица возможностей не нужна.
- **Один раздел `tree`, а не `commit-tree`.** Вид раздела задаёт scope, а не отдельный kind.
- **Сравнение начинается со списка изменений.** Ленивое дерево снимка и плоский список изменений — разные модели; общий у них `FileChange`, пометки и строка. Union-дерево добавляется только под конкретный сценарий и только на стороне чтения.
- **Live-ключи не меняются.** Сессии и кеши рабочей копии сохраняют прежний вид.
- **MR — адаптер, а не compare scope.** `pull-files` остаётся источником истины для merge request; общий словарь и `ChangesTree` дают единый вид без подмены ревизий.
- **HTML и архивы снимка отключены явно.** Вместо тихого падения вкладка показывает, что HTML открыт как код, а архив не распаковывается.

## Следующие этапы

1. **Merge request.** Решено: `pull-files`/`pull-diff` остаются адаптером за общим `FileChange` и `ChangesTree`; compare scope для MR не вводим.
2. **Просмотрщики.** Markdown, изображения и SVG на коммите готовы. HTML и архивы на снимке отключены с подписью; отдельная поддержка — только при появлении реального сценария.
3. **Поиск в снимке.** Локальный `git grep <rev>` и GitLab blob search по `ref` готовы. GitHub не поддерживает поиск по произвольному коммиту через API; отдельный индекс или клон — только при появлении потребителя. Выбор ревизии уже идёт из истории и команды `ide.workbench.tree.open`.

## Открытые вопросы

- Сравнение двух произвольных папок на диске — отдельный scope с allowlist, не в первом этапе.
- Полное union-дерево — только если понадобится показывать неизменённые файлы в сравнении; тогда расширять `TreePage`, а не UI.
- Переименования — показывать как deleted + added; `originalPath` использовать для подписи и перехода.
- Индекс — не добавлять в `FileScope`, пока не появится отдельное дерево индекса: у него другая семантика.
- Кто владеет ревизией — раздел или команда передаёт готовый хеш; scope хранит только его.
- GitLab blob search зависит от Advanced Search; на инстансе без него показывается ошибка, а не пустой результат. GitHub-поиск по снимку не добавляем без отдельного механизма (индекс, клон или API с ref).

## Чего не делать

- Не заводить профиль на каждый коммит: профиль — источник и его возможности, а не позиция в истории.
- Не протаскивать `rev` строкой через все вызовы: снимок передаётся как scope, параметры добавляет один адаптер.
- Не делать второе дерево «для истории»: отличаться должен источник, а не компонент.
- Не считать `commit-diff` готовым деревом: он отдаёт только изменённые файлы.
- Не вводить `FileSource`/`FileSourceCapabilities` без нового реального потребителя.
