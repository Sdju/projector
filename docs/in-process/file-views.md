# Файловые представления: дерево на коммите и diff директорий

Рабочий документ: только открытые решения и план. Текущее устройство — [architecture.md](../architecture.md) («Профили workspace»), [usage.md](../usage.md) («Файлы и поиск»), [ide-commands.md](../ide-commands.md). Здесь не дублируются контракты, которые уже описаны.

## Задача

Панель файлов сейчас показывает рабочую копию проекта. Нужен универсальный файловый адаптер, который умеет отдать:

- дерево на произвольном коммите;
- сравнение двух снимков (ревизий или директорий) с пометками;
- в перспективе — другие источники: индекс, контейнер, том.

Сразу всё не обязательно. Сначала контракт и read-only деревья, затем сравнение.

Первый срез уже в коде: `historyTree` в профиле, `tree`/`file` с `rev` на сервере, read-only дерево коммита в боковой панели, группировка иконок разделов, подпись источника над панелью и закрытие временного раздела (ПКМ на ПК, кнопка на телефоне). Открытые пункты ниже — сравнение снимков, общий `FileScope`/фасад источника, отдельная вкладка/скоуп для ссылок и ассетов, поиск и HTML/архивы.

## Что уже есть

- `FilesProvider.read` (`tree`, `file`, `paths`, `search`, `asset`, `root`) и `GitProvider` (`commit`, `commit-diff`, `diff`, `gutter`).
- Дерево уже страничное (`TreePage`, `treePageRange`), а GitHub и GitLab уже читают дерево по sha: `readTree(repository, sha)`; `assetUrl` у GitHub уже прибит к `metadata.tree`.
- В открытых вкладках уже есть три «базы»: рабочая копия, индекс (`staged`) и diff коммита (`commit-diff`); `OpenFile.original` и CodeViewer уже показывают две стороны.
- Git-пометки дерева считаются из `GitOverview` отдельно (`gitTreeDecorations`), а не приходят вместе с деревом.
- Дерево и вкладки умеют жить в отдельных блоках и восстанавливаться из сессии; типы вкладок регистрируются.

Вывод: понятие «читать файл из другого места» уже размазано по трём местам. Нужно не изобрести его, а сделать явным.

## Статус первого среза

Сделано:

- `historyTree` — возможность профиля; локальный профиль читает `tree`/`file` с `rev`, удалённые GitHub/GitLab пока её не объявляют.
- Временный раздел «Файлы коммита @hash» в группе Git: общая подложка с родительской иконкой, сепараторы между снимками, подпись «Только чтение · коммит hash» в шапке панели.
- Вход из обзора коммита и контекстного меню истории; закрытие через ПКМ на иконке (ПК) или кнопку в шапке панели (телефон), обе — через `ide.workbench.section.close`.
- Дерево read-only: команды записи, DnD и импорт выключены; вложенные папки читаются из того же коммита; статусы `A/M/D/R` берутся из обзора коммита.
- Файлы снимка открываются в read-only-вкладках (`OpenFile.rev`); наблюдение за диском, сохранение, gutter и восстановление таких вкладок из сессии отключены.
- Серверные тесты дерева/файла на ревизии и тесты группировки разделов.

Временные отклонения первого среза (это долг, а не финальный контракт):

- Вместо `FileScope` и `FileSource` — `rev` в `tree`/`file` и `OpenFile.rev`. Перед сравнением снимков фасад нужно ввести и убрать `rev` из случайных вызовов.
- Read-only выражен prop `readonly` у `FileTree`; отдельного `FileSourceCapabilities` пока нет. `useTreeOperations` фиксирует `writable` при создании scope — для динамического переключения источника этого не хватит.
- Динамические разделы и read-only-вкладки не переживают перезагрузку; это осознанно, чтобы не восстанавливать вкладку без дерева.
- Markdown, HTML, SVG, изображения и архивы на ревизии пока не открываются своими просмотрщиками; ссылки и ассеты внутри снимка остаются вне scope.

## Ось: FileScope

```ts
export type FileScope =
  | { kind: "live" } // рабочая копия
  | { kind: "commit"; rev: string } // снимок коммита
  | { kind: "compare"; from: string; to: string }; // два снимка
```

- `rev`/`from`/`to` — конкретные хеши, а не имена веток: снимок не должен «поехать» под открытой вкладкой. Имя ветки можно показать в подписи.
- `FileScope` не содержит git-команд и путей на диске: как его прочитать, решает провайдер. Это оставляет место для `index`, контейнера и сравнения папок без Git.
- Ключ для вкладок, сессий и кешей: `live`, `commit:<hash>`, `compare:<a>..<b>`.

Фасад вместо `base` в каждом вызове:

```ts
interface FileSource {
  readonly key: string;
  readonly label: string;
  readonly editable: boolean; // только live и write провайдера
  readonly watchable: boolean; // только live
  tree(params): Promise<TreePage>;
  file(path): Promise<FileContent | FileComparison>;
  assetUrl(path, external?): string;
  status?(): Promise<FileStatusMap>; // пометки для дерева
}
workspaceFileSource(projectId, scope): FileSource;
```

`workspaceRequest(projectId, "tree", { path })` остаётся для live. Новые вызовы идут через источник. Внутри `workspace-api` источник выбирает, к какому провайдеру идти: live — к `files`, исторические — к `git`/`history`. Адаптеры не знают о UI, UI не знает о git-командах.

## Возможности — у источника, а не у проекта

Сейчас `write`, `watch`, `search` — свойства `WorkspaceProfile`, то есть проекта. Для исторического дерева это неверно: тот же проект, но писать нельзя и следить не за чем.

- `WorkspaceCapabilities` оставить для функций проекта (терминалы, Docker, агент, настройки, persist, externalFiles).
- Рядом ввести `FileSourceCapabilities { write, watch, search, assets, archive }`.
- Команды `ide.fileTree.*`, которым нужна запись, проверяют не `workspaceCapabilities(projectId).write`, а `activeSource.editable`; `enabled` должен пересчитываться при смене источника.
- `useTreeOperations` сейчас фиксирует `capabilities` и `requires` при создании scope. Для read-only дерева нужен либо отдельный набор команд, либо `canWrite()` внутри `enabled`.

В первом срезе сделан только временный вариант: `historyTree` гейтит вход, а конкретное дерево получает `readonly` prop. `FileSourceCapabilities` и динамический `canWrite()` остаются открыты. Это единственное настоящее архитектурное изменение: право на действие переезжает из профиля в представление.

## Куда проникает ось

| Слой                     | Что меняется                                                                                                       | Цена             |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------ | ---------------- |
| `core/modules/workspace` | `FileScope`, статус записи, расширение `TreePage`/`FileEntry`; обратная совместимость                              | низкая           |
| `workspace-api`          | фасад источника, разбор scope, права на источник, ключи кешей                                                      | средняя          |
| Провайдеры и сервер      | локальный снимок через `git`, сравнение, `tree`/`file`/`asset` с `rev`; GitHub/GitLab — по sha                     | средняя          |
| `tree`                   | prop источника, идентичность листинга, ключ сессии, read-only команды, `selected`/`reveal`, отключение DnD/импорта | средняя          |
| Открытые файлы и вкладки | scope в ключе и `OpenFile`, сессия, `file-sync` только для live, сохранение только для editable                    | средняя, широкая |
| Просмотрщики             | read-only, подписи diff, ссылки Markdown, ассеты, HTML и архивы                                                    | средняя          |
| Команды и документация   | scope в контексте и аргументах, новые команды открытия                                                             | низкая           |
| Тесты                    | дерево на ревизии, union-сравнение, read-only команды, сессия                                                      | средняя          |

По объёму это средняя фича, а не рефакторинг ядра. Основная стоимость — не Git и не сервер, а сквозная идентичность `(scope, path)` и разделение прав.

## Где настоящая сложность

1. **Сравнение — это объединённое дерево, а не список изменённых файлов.** Удалённых файлов нет на «правой» стороне, поэтому `FileEntry` должен уметь представлять запись, которой нет в снимке; сейчас удаление — только пометка на существующей строке. Варианты: union с `status` (рекомендую) или отдельный список изменённых (он уже есть в обзоре коммита). При union листинг остаётся ленивым: для каждой папки читаем две стороны, объединяем имена, статус агрегируем (`gitTreeDecorations` уже умеет).
2. **Переименования.** В дереве показывать как deleted + added; не менять модель ради одной строки. Связь старая → новая уже есть в `GitCommitFile.originalPath`.
3. **Пометки коммита.** Не вызывать `projectCommit` на каждую страницу дерева: один `git diff --name-status` на scope и кеш. Для live оставить `GitOverview`.
4. **Идентичность.** Путь перестаёт быть ключом. Вкладка, selection, `selected`, `reveal`, сессия и кеш — везде `(scope, path)`. Live-ключи лучше не менять, чтобы старые сессии открывались.
5. **Наблюдение и обновление.** Только live подписывается на изменения; pinned обновляется явным refresh. Ветки резолвить в хеши при открытии.
6. **Ссылки и ассеты.** README на коммите должен открывать соседний файл из того же коммита, картинки — из того же дерева. `MarkdownViewer @open`, `assetUrl`, `siteUrl` должны знать scope. HTML-предпросмотр и архивы на ревизии — отдельная работа; в первом этапе их можно отключить.
7. **`.gitignore` и `files.exclude`.** Excludes остаются настройкой просмотра. Приглушение ignored на историческом дереве либо по правилам ревизии (читать blob), либо не делается; смешивать их нельзя.
8. **Кеш удалённых провайдеров.** Ключ каталога сейчас `tree:path`; станет `scope:path`. Инвалидация — по scope, не глобально.
9. **Команды агента.** Без scope в контексте и аргументах агент не сможет открыть дерево коммита. Это часть контракта, а не полировка.

## UX: где показывать историческое дерево

**Вариант A: режим панели «Файлы»** (переключатель рабочая копия / коммит). Дёшево по разметке, дорого по последствиям: selection, reveal, watch, write-команды, сессия и «активный файл» начинают зависеть от режима; нельзя открыть два снимка рядом.

**Вариант B: временный раздел боковой панели.** Иконка того же вида, что у файлов, стоит в группе Git: общая подложка с родительской иконкой, сепараторы между несколькими снимками. Сайдбар остаётся живым для остальных разделов; дерево снимка read-only; рядом можно держать несколько коммитов. Минусы: временные разделы не переживают перезагрузку (их вкладки тоже не сохраняются), а selection/reveal надо привязывать к разделу. Реализовано в первом срезе.

**Вариант C: отдельная вкладка `tree` с параметром `{ scope }`**, как `commit` и `browser`. Dock уже умеет несколько блоков, перенос и сохранение; снимок можно положить рядом с рабочим деревом. Минус: отдельная surface и своя сессия; пока не выбрано.

Решение первого среза: историческое дерево — временный read-only раздел в группе Git; рабочая панель «Файлы» не меняет режим. Если понадобится вкладка, фасад источника уже будет готов.

## Этапы

0. **Контракт и чтение.** Базовый срез сделан: `historyTree`, `tree`/`file` с `rev`, локальный снимок коммита, тесты. Полный `FileScope` и фасад источника (общий для live/commit/compare) ещё открыты; текущий `rev` — временный компромисс.
1. **Read-only дерево коммита.** Сделано: временный раздел в группе Git, вход из обзора и контекстного меню, статусы из коммита, подпись источника, закрытие через ПКМ/кнопку, вложенные папки из того же коммита, read-only-вкладки. Не сделано: открытие diff-вкладок прямо из дерева, сохранение раздела в сессии, отдельный `reveal`-контракт для источника.
2. **Сравнение снимков.** Union-дерево, deleted-записи, две стороны файла, переключатель базы.
3. **Полировка.** Ссылки и ассеты в scope, сессия, команды агента, GitHub/GitLab, выбор ревизии, кеш. Отдельно решить про поиск, HTML и архивы.

## Открытые вопросы

- «Разница между директориями» — это две ревизии Git или две произвольные папки на диске? От ответа зависит, нужен ли scope с путями и allowlist.
- Точка входа первого среза — обзор коммита и контекстное меню. Нужны ли отдельные входы из истории, веток и палитры команд?
- Нужен ли поиск внутри снимка (`git grep <rev>`) и переходы по Markdown-ссылкам в первом этапе?
- Показывать ли переименования одной строкой или двумя?
- Нужен ли режим «индекс» как отдельный снимок? Сейчас индекс виден только в diff одного файла.
- Кто владеет выбором ревизии: диалог истории, URL вкладки или отдельная команда? В первом срезе ревизия приходит из уже открытого коммита.
- Сохранять ли временные разделы и их read-only-вкладки в сессии? Сейчас они намеренно эфемерны.

## Чего не делать

- Не заводить профиль на каждый коммит: профиль — это источник и его возможности, а не позиция в истории; иначе резолвер, сессии и вкладки размножатся.
- Не протаскивать `rev` строкой через все вызовы `workspaceRequest`: через месяц появится второй вид снимка, и каждый вызов будет знать о Git. В первом срезе `rev` уже проник в `tree`/`file` как временный компромисс — перед сравнением его нужно убрать за `FileSource`.
- Не делать второе дерево «для истории»: отличаться должен источник, а не компонент.
- Не считать `commit-diff` готовым деревом: он отдаёт только изменённые файлы и не умеет неизменённые и удалённые узлы.
