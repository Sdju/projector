# 0.3.0: GitHub и контейнерные окружения

План обновлён 2026-10-04 по текущей реализации. Версия приложения пока 0.2.0; этот документ описывает готовые части и оставшиеся задачи, а не объявляет выпуск 0.3.0. Инструкции по текущему использованию: [GitHub](integrations.md), [Docker](docker.md).

## Цель и текущий сценарий

Открыть внешний репозиторий, изучить его без загрузки на диск, затем при необходимости клонировать и запускать в ограниченном окружении. После клона открывается обычный workspace `/projects/...`; локальные проекты сохраняют свой способ запуска.

Сейчас цепочка выглядит так: `gh:/owner/repository` → просмотр файлов и истории → окно клонирования → папка назначения, образ, сеть и порты → подготовка образа и clone → workspace → ручная установка зависимостей и запуск из терминала. Окно выбирает Docker по умолчанию. Установка зависимостей и запуск кода при клонировании автоматически не выполняются.

Удаление проекта закрывает его терминалы и удаляет запись каталога, но сохраняет файлы. Автоматического перевода Docker-проекта в host-режим нет. Изменение проекта через обычный PATCH сохраняет его environment и путь.

## Принятые решения

### Ограниченный Docker вместо автоматического Dev Container CLI

Первый срез использует управляемый `docker run`, а не `@devcontainers/cli`. Зависимость CLI не добавлена. Проект может выбрать доверенный образ с Bash и Git; параметры запуска формирует Projector. Репозиторные `devcontainer.json`, Dockerfile, Features, Compose, mounts и lifecycle hooks автоматически не исполняются.

Это сознательное ограничение текущего сценария безопасности. Полную поддержку Dev Containers вынести в отдельный этап после политики конфигураций и проверки всех исполняющих стадий. Не передавать репозиторную конфигурацию движку до такой проверки и не называть нынешний режим полной реализацией стандарта.

### Checkout на хосте, отдельные временные контейнеры

Рабочие файлы сейчас находятся в выбранной пользователем папке, а не в служебном `$XDG_DATA_HOME/projector/workspaces`. Каждый контейнер получает только этот checkout в `/workspace`. Файлы и зависимости внутри папки сохраняются; rootfs, HOME и /tmp не являются хранилищем проекта. Терминалы разделяют файлы, но не процессы и временные домашние папки.

Named volumes, общие кеши, длительно работающий контейнер и служебный checkout остаются отдельными вариантами развития. Для volumes потребуется filesystem provider; API не должен читать `/var/lib/docker/volumes` напрямую. Удалённый Docker пока вне scope: допускаются локальные contexts с Unix socket.

### Явная сеть и отсутствие host fallback

Для clone временно включается bridge, чтобы получить репозиторий по HTTPS. Для выполнения по умолчанию используется `none`; разрешение bridge в окне открывает интернет и LAN. Порты публикуются только на loopback. Нет Docker socket, host HOME и переноса настроек/секретов хоста в runtime-контейнеры.

Git-операции изолированного checkout также выполняются внутри Docker, с отключёнными hooks. Bash агента не может сменить cwd такого проекта на хост. Отказ Docker не должен приводить к запуску команды на хосте. Ограничение ядра Docker и отсутствие квот описаны в документации, поэтому абсолютная безопасность произвольного вредоносного кода не обещается.

## Правила будущего экспорта

Копирование и переход в host-режим — разные операции. Сохранять .git, tracked/untracked изменения, dotfiles и пользовательские файлы. Исключения для зависимостей и generated files задавать явно; не выбрасывать все gitignored данные. Rootfs, процессы и данные дополнительных volumes не считать частью checkout; для БД нужен отдельный backup/export.

Публиковать временную копию на целевой файловой системе с отказом при коллизии. Не выполнять неявный merge с существующей папкой. При ошибке исходные файлы и окружение остаются доступными; их удаление — отдельное действие после успешного экспорта. Переход в host-режим требует остановки сессий и явного изменения профиля выполнения.

## Фактически проверено на 2026-10-04

- `vp run check`: архитектура FEOD, тесты, типы и сборка прошли; `git diff --check` прошёл. Проверка включает fixtures GitHub API/clone и Docker CLI; это не live-проверка OAuth или приватного clone.
- Настоящий Docker daemon: образ `node:24-bookworm`, запуск под UID 1000, отсутствие Docker socket и файлов настроек хоста, запрет записи в /etc и root HOME, отключённая runtime-сеть и сохранение файла checkout.
- Chromium: публичный `octocat/Hello-World` клонирован через окно внутри Docker, открыт `/projects/...` с сохранённым профилем; Shell принимает ввод, созданный файл виден Git; перезагрузка страницы восстановила ту же PTY-сессию.
- Настоящий HTTP-сервис внутри контейнера: runner получил фактический случайный порт, ответ доступен через 127.0.0.1, Docker binding ограничен loopback.
- Bash агента: выполнение в Docker, сохранение ненулевого exitCode и отказ при попытке сменить cwd на папку хоста.
- Закрытие PTY, остановка runner, удаление тестового проекта и SIGTERM отдельного тестового серверного процесса удалили их контейнеры. Действующий сервер ради проверки не перезапускался; временный checkout и запись каталога очищены.
- Live (`vp run test:live`, настоящий Docker): UID хоста, нет Docker socket и host HOME, rootfs read-only, нет сети и capabilities, секретные переменные хоста не передаются, два проекта публикуют один внутренний порт на разных 127.0.0.1-портах, неверный context не приводит к запуску на хосте, остановка во время создания не оставляет контейнера, очистка осиротевших контейнеров оставляет чужие и текущие, Dev Container: `initializeCommand` на хосте только после доверия, `postCreateCommand` и Bash внутри.
- Chromium: окно доверия, запуск терминала в Dev Container, повторный вопрос после правки конфига. Отмена клонирования во время `docker pull` через API: фаза `pulling → cancelled`, проект не добавлен, процессов и временных папок не осталось.
- Не проверено live: private Docker clone, реальный OAuth Device Flow, установка AI CLI, автоматическая подготовка зависимостей, Dev Container с Features и Compose.

Холодный/тёплый запуск и размер кешей пока не измерялись. Для ускорения сначала измерить время до терминала и до приложения; затем выбирать кеши и повторное использование окружений с сохранением границ доступа.
