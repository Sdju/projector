# Делегирование и оркестрация

Штатный агент Projector не пишет код сам: он раздаёт работу фоновым кодовым агентам, следит за ней и показывает пользователю результат. Здесь описано, что уже работает, чего не хватает и в каком порядке это делается.

Связанные документы: [фоновые агенты](agent-background.md), [ветки чатов](chat-forks.md), [SDK команд](ide-commands.md), [возможности агентов](agent-features.md).

## Состояние

Сделано: точные ответы на вопросы и запрет разрешений из модели, `ide.agent.job.diff` и `ide.agent.job.log`, полный итог, карточки запросов и полоса заданий в чате Projector, автопродолжение, досылка в то же задание (`send`/`continue`), форк копии (`fork`), `retry` с нуля, `ide.agent.job.worktree/merge/discard`, снятый потолок в 4 задания, evals-сценарий делегирования. Осталось: очередь при реальной нехватке ресурсов — сейчас задания стартуют сразу.

## Что уже работает

Фоновое задание — ход Claude Code, Codex, OpenCode, Cursor или Kimi Code, который сервер ведёт без открытой вкладки. Штатный агент запускает его командой и забирает результат.

| Команда                                | Что делает                                                                                         |
| -------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `ide.agent.job.start`                  | Запускает задание: `agent`, `task`, `isolate?`; возвращает запись задания                          |
| `ide.agent.jobs.list`                  | Задания проекта: состояние, ожидающие запросы, файлы, начало итога                                 |
| `ide.agent.job.result`                 | Состояние и полный итог; `wait` до 45 с ждёт смены состояния                                       |
| `ide.agent.job.diff`                   | Файлы, `--stat` и patch того, что сделало задание                                                  |
| `ide.agent.job.log`                    | Последние вызовы инструментов и их вывод                                                           |
| `ide.agent.job.stop`                   | Останавливает задание, сделанное остаётся в файлах                                                 |
| `ide.agent.job.answer`                 | Отвечает на вопросы задания по идентификаторам вариантов; разрешения выдаёт пользователь карточкой |
| `ide.agent.job.send`                   | Уточнение: идущему — в текущий ход, завершённому — новый ход в той же записи                       |
| `ide.agent.job.retry`                  | Повтор с нуля в новой записи, той же копии и сессии                                                |
| `ide.agent.job.continue`               | То же, что `send` для завершённого задания                                                         |
| `ide.agent.job.fork`                   | Новая копия из текущего состояния копии задания                                                    |
| `ide.agent.job.worktree/merge/discard` | Осмотр, слияние и удаление копии задания                                                           |
| `ide.agent.job.open`                   | Открывает вкладку задания: журнал, итог, файлы, запросы                                            |

Задание живёт на сервере (`$XDG_DATA_HOME/projector/agent/jobs/<id>/`), переживает перезапуск, видно в острове активности и во вкладке, уведомляет о завершении и об ожидании пользователя. Состояния: `queued`, `running`, `needs-user`, `done`, `error`, `stopped`. Изоляция — обычный `git worktree`, слияние только по просьбе пользователя.

## Решения

1. **Разрешения решает пользователь, а не модель.** Ожидающий запрос задания показывается карточкой в чате Projector; ответ уходит прямо в задание. Модель видит только «ждёт разрешения» и не может нажать «разрешить».
2. **Чат продолжается сам.** Когда задание завершилось (`done` или `error`), ход Projector возобновляется с результатом; ожидание пользователя показывают карточки, отдельный клик не нужен.
3. **Изоляция остаётся ручной.** `isolate: true` передаёт штатный агент, когда задачи могут мешать друг другу; по умолчанию задание работает в папке проекта.
4. **Очередь вместо искусственного потолка.** Предела «4 задания» нет: задания стартуют сразу. `queued` — короткое состояние до запуска; если ресурсов действительно не хватит, задание останется в очереди, а не получит отказ. Обрезка итога в команде тоже убрана: ответ читается целиком, хранилище защищено отдельно.

## Модель

- **Задание** — один ход внешнего агента, которым управляет сервер. Вкладка не нужна; журнал и итог доступны командами и во вкладке.
- **Чат Projector** — оркестратор. Он запускает задания, показывает их как задачи, передаёт пользователю запросы разрешений и объясняет результат.
- **Чат внешнего агента** — обычный графический чат. Он остаётся для ручной работы и для продолжения задания, когда нужен диалог.

Штатный агент не получает файловых инструментов и не откатывает файлы: это по-прежнему работа кодовых агентов. Делегирование — не новая подсистема, а связка существующих чатов, заданий и рабочей области.

## Этапы

### 1. Точные запросы

Сейчас `ide.agent.job.answer` передаёт только текст, а описание вопроса показывает подписи вариантов без идентификаторов. Многошаговый вопрос и `multiple: true` отвечаются угадыванием.

- В описании задания отдавать `id` вопроса и `{ id, label }` каждого варианта.
- В `ide.agent.job.answer` принимать `answers: Record<id, string[]>` и передавать его в API; разрешения — только явными `allow`, `always`, `deny`.
- Готово, когда задание с двумя вопросами и множественным выбором отвечается по идентификаторам, а не по тексту.

### 2. Проверяемый результат

`ide.agent.job.result` обрезает ответ и не показывает, что именно изменилось и чем это проверено. Промпт требует «сверяй с git diff», но diff приходится добывать оболочкой.

- `ide.agent.job.diff` — изменённые файлы, `--stat` и patch с пределом; для копии — из её папки.
- `ide.agent.job.log` — последние вызовы инструментов, команды проверок и их код возврата.
- Полный итог в `ide.agent.job.result`: без обрезки, ответ читается целиком.
- Готово, когда штатный агент объясняет, что изменено и какие проверки прошли, не запуская bash.

### 3. Разрешения в чате

- Ожидающий запрос задания превращается в карточку разрешения или вопроса в чате Projector — ту же, что у обычного чата.
- Ответ пользователя уходит прямо в задание; модель видит только ожидание и не может подтвердить разрешение (`ide.agent.job.answer` отвечает лишь на вопросы).
- Если чат закрыт, работают вкладка задания и уведомление.
- Готово, когда сценарий проверки доказывает: без действия пользователя `allow` не появляется.

### 4. Видимость и автопродолжение

- `job.start` показывает задание полосой в чате Projector: агент, тема и состояние; клик открывает вкладку.
- Завершение и `needs-user` обновляют полосу; завершение запущенного задания возобновляет ход чата с результатом. Автопродолжение включено по умолчанию.
- Готово, когда после делегирования в чате видна задача, а её завершение само приносит итог в разговор.

### 5. Копии и продолжение

- `ide.agent.job.worktree`, `ide.agent.job.merge`, `ide.agent.job.discard` — осмотр, слияние и удаление копии задания; слияние и удаление только по просьбе пользователя.
- `ide.agent.job.fork` — вторая копия с текущим состоянием работы задания для альтернативного варианта.
- Изолированное задание продолжается новым ходом в той же записи, копии и сессии (`ide.agent.job.send` или `continue`); обычный чат к копии не подключается: сессия привязана к папке копии.
- Готово, когда копию задания можно осмотреть, слить или выбросить командой, а конфликт не ломает проект.

### 6. Очередь и управление ходом

- Потолок в 4 задания убран: задания стартуют сразу. `queued` остаётся коротким состоянием до запуска; отдельной очереди с позицией нет.
- `ide.agent.job.send` — уточнение: идущему ходу, если агент умеет, иначе ошибка; завершённому — новый ход в той же записи, копии и сессии, без создания второго задания.
- `ide.agent.job.retry` — повтор с нуля в новой записи, той же копии и сессии; `ide.agent.job.continue` — то же, что `send` для завершённого.
- `ide.agent.job.fork` — отдельная копия из текущего состояния копии задания: незакоммиченная работа фиксируется на ветке исходной копии, исходное задание не меняется.
- Готово, когда десятое задание не отклоняется, уточнение доходит до агента, а повтор не плодит копии.

### 7. Проверки

Сценарии в `evals/`:

- код уходит заданию, а не пишется самим агентом;
- агент не верит итогу без diff;
- не разрешает без пользователя;
- не сливает копию без просьбы;
- отвечает на `needs-user`;
- продолжает разговор после завершения задания.

Прогон на двух моделях по три раза, результаты сохраняются для сравнения. Готово, когда сценарии зелёные, а не «зелёные один раз руками».

## Безопасность

- Разрешения и вопросы задания решает пользователь; модель передаёт только факт ожидания.
- `always` и «без вопросов» не включаются моделью.
- Слияние и удаление копии — только по явной просьбе; автослияния нет.
- Задание запускается с подтверждением старта; параметры задания проверяются на сервере, пути берутся из реестра проектов.
- Артефакты задания (журнал, итог) считаются недоверенными: промпт требует сверять их с diff.

## Чего не делаем

- Автослияние копий и автоматический откат файлов.
- Вложенное делегирование глубже одного уровня.
- Планировщик и триггеры по событиям.
- Задания для TUI-режима.
- Свои файловые инструменты у штатного агента.

## Защитные пределы

Убираются искусственные ограничения: потолок одновременных заданий и обрезка ответа в команде. Остаются пределы, у которых есть реальная причина: размер журнала, срок хранения завершённых заданий, таймауты ожидания разрешения и лимит текста задания.
