# Производительность и пределы

Ориентиры, чтобы оценивать архитектурные изменения и не искать заново узкие места. Цифры ниже — замер на localhost; это порядок величин, а не SLA.

## Пределы

- `MAX_SESSIONS = 24` терминальных сессий (`server/modules/terminal/session-state.ts`); 25-я возвращает «Лимит терминалов».
- Сервер однопоточен для ввода-вывода: вывод PTY, снимки экрана (`@xterm/headless`) и HTTP делят одно ядро.
- Один поток вывода PTY даёт 12–34 МБ/с на сессию; при медленной отрисовке чтение PTY приостанавливается до подтверждения браузера.
- Клиент держит 5000 строк истории терминала; после 1 млн строк память renderer растёт примерно вдвое.
- Слежение за файлами — `fs.watch` без рекурсии, только раскрытые папки и открытые файлы (лимиты 300 папок и 200 файлов на реестр, `server/modules/workspace/watcher.ts`).
- Dev-режим тяжелее prod в 7–8 раз по памяти; это цена Vite, native и HMR, а не пользовательских данных.

## Порядок величин

| Показатель                                  | Значение             |
| ------------------------------------------- | -------------------- |
| Prod-сервер в простое                       | ~141–150 МБ RSS      |
| Dev целиком (`vite dev` + native + обёртка) | ~1,1 ГБ              |
| Вкладка в Chromium в простое                | ~55 МБ PSS renderer  |
| Вкладка после 1 млн строк в терминале       | ~121 МБ PSS          |
| Всё приложение в простое (сервер + вкладка) | ~220 МБ              |
| Один проект на сервере                      | ~+0,8 МБ             |
| Один проект во вкладке                      | ~+3–7 МБ PSS         |
| Эхо клавиши через сервер                    | p50 1,3 мс           |
| Вывод PTY                                   | 12–34 МБ/с на сессию |
| `/api/health`                               | p50 0,55 мс          |
| Сборка `dist`                               | ~6,3 МБ, 215 файлов  |

Основной расход в нескольких проектах — процессы пользователя (шелл и dev-серверы), а не сервер или вкладка. После пика нагрузки RSS сервера возвращается с задержкой порядка минуты; это не подтверждённая утечка.

## Чат

Замер `vp run bench:chat` (скрипт [`scripts/bench-chat`](../scripts/bench-chat/README.md)): настоящие `AgentTurn`/`AgentMessage` в headless Chromium 154, окно чата 900×900, колонка 680 px, ответы по 1,2 КБ, поток кусками 64–256 символов. Dev-сборка Vue: абсолютные числа выше production, важны соотношения.

| Сценарий                                        | Значение                     |
| ----------------------------------------------- | ---------------------------- |
| Открытие чата из 5 запросов                     | ~23 мс, 393 узла             |
| Открытие 250 запросов (всё смонтировано)        | ~883 мс, 19 258 узлов        |
| Открытие 10 000 запросов через окно             | ~29 мс, 10 сообщений         |
| Добавление запроса: окно 5 / всё 500            | ~8 / ~17 мс                  |
| Смена чата: 250 запросов / окно при 1000        | ~130 / ~5 мс                 |
| Поток 8 КБ при 5 / 200 запросах в чате          | 0,3 / 1,3 с                  |
| Задержка куска потока 8 КБ при 5 / 200          | p50 4,7 / 23,8 мс            |
| Поток прозы 32 КБ кусками по 64                 | 2,2 с, p95 5,5 мс            |
| Поток кода 24 КБ кусками по 64                  | 7,9 с, p95 39 мс             |
| Одно обновление открытого блока кода 32 / 96 КБ | 6,5 / 19 мс                  |
| Одно обновление прозы 96 КБ                     | 0,7 мс                       |
| Открытие ответа 256 КБ прозы                    | ~322 мс                      |
| 24 виджета / 200 вызовов в закрытой «Работе»    | ~5 / ~9 мс, 80 узлов         |
| Раскрытие «Работы» с 200 вызовами               | ~65–75 мс, 3 757 узлов       |
| 100 рассуждений в закрытой «Работе» / раскрыто  | ~3 / ~23 мс, 80 / 1 481 узел |
| Память renderer при 500 запросах (после GC)     | 65 МБ, +~105 КБ/запрос       |

- Окно из последних пяти запросов держит цену открытия и потока постоянной: 10 000 запросов в истории не отличаются от 10.
- Полный монтаж линеен, ~3,5 мс и ~77 DOM-узлов на запрос; после этого прокрутка идёт 60 fps, но первый кадр полного чата на 250 запросов даёт скачок ~200 мс.
- Один открытый блок кода в потоке переразбирается каждый раз: 32→96 КБ ускоряют обновление втрое, а весь поток — квадратично. Проза инкрементальна, её обновление почти не растёт.
- Троттлинг `AgentMarkdown` сохраняет 60 fps и p95 кадра 16,7 мс ценой задержки отдачи: 24 КБ кода идут 7,9 с при p95 задержки куска 39 мс. Без троттлинга те же 96 КБ кода дают 19 мс на обновление — заметный блок кадра.
- Прокрутка вниз во время потока добавляет к 32 КБ прозы ~10% времени и единичный кадр 66 мс.
- Закрытая «Работа» держит в DOM только заголовок: 200 вызовов — 80 узлов вместо 3 749 и ~9 мс вместо ~78 мс на открытие; 100 рассуждений — 80 узлов и ~3 мс. Раскрытие монтирует их за ~65–75 и ~23 мс, то есть расход перенесён на явное действие. Поток 8 КБ рядом с 200 вызовами: ~0,12 с и 1,6 мс на обновление в закрытом блоке против ~1,2 с и 14 мс в открытом.

## Как мерить

Чтобы не трогать рабочий инстанс на 4177, запускайте отдельный процесс с изолированными данными. Порт 4190 использовать нельзя: он в блок-листе `fetch`.

```bash
S=$(mktemp -d)
cd <repo>
export XDG_DATA_HOME=$S/data XDG_CONFIG_HOME=$S/data/cfg PROJECTOR_PORT=4213
node server/app/standalone.ts &
curl -s localhost:4213/api/health            # поле "pid"
grep -E 'VmRSS|VmHWM' /proc/<pid>/status
grep -E 'Rss|Pss|Anonymous' /proc/<pid>/smaps_rollup
```

- **HTTP**: последовательные `fetch` с прогревом, затем перцентили; пропускная способность — 32 параллельных цикла.
- **Терминалы**: `POST /api/projects/<id>/terminals` `{"program":"shell"}` с заголовком `Origin`, затем WebSocket `/api/terminal/socket?session=<id>`; клиент подтверждает каждый `output` сообщением `{"type":"ack","length":N}`.
- **Клиент**: `performance.getEntriesByType('navigation')`, `performance.memory`, подсчёт DOM-узлов в открытом проекте.
- **Память**: `process.memoryUsage()` и `v8.getHeapSpaceStatistics()`; состав RSS — `/proc/<pid>/smaps_rollup`.

Подводные камни:

- Не используйте `pkill -f`/`pgrep -f` с именем скрипта в той же оболочке: совпадёт и она сама.
- После прогона закрывайте сессии (`DELETE` требует `confirmation` из `GET` сессии) или перезапускайте сервер: сессии живут в процессе.
- Не совмещайте замер памяти до и после нагрузки в одном процессе, если нужен «чистый простой»: RSS не откатывается сразу.
- Долгие прогоны с HMR проверяйте отдельно: рост памяти в dev обычно связан с конфигурацией Vite и окружением, а не с бизнес-логикой. Регрессии жизненного цикла: `tests/runtime-lifecycle.test.mjs`, `tests/instance-exit.test.mjs`, `tests/window-host-lifecycle.test.mjs`, `tests/windows-protocol.test.mjs`, `tests/restart.test.mjs`, `tests/environment-runtime.test.mjs`.

## Что не покрыто

Реальные большие репозитории (monorepo, `node_modules`, 100k+ файлов), типовые dev-инструменты внутри терминалов, длительная работа с периодическим снятием памяти, Docker/devcontainer под нагрузкой, LAN с несколькими клиентами и строгое сравнение с VS Code на том же железе.
