# Производительность и пределы

Ориентиры, чтобы оценивать изменения и не искать узкие места заново. Цифры — замер на localhost, порядок величин, не SLA.

## Пределы

- `MAX_SESSIONS = 24` терминальных сессий (`packages/server/modules/terminal/session-state.ts`); 25-я получает «Лимит терминалов».
- Сервер однопоточен для ввода-вывода: вывод PTY, снимки экрана (`@xterm/headless`) и HTTP делят одно ядро.
- Один поток PTY — 12–34 МБ/с на сессию; при медленной отрисовке чтение приостанавливается до подтверждения браузера.
- Клиент держит 5000 строк истории терминала; после 1 млн строк память renderer растёт примерно вдвое.
- Слежение за файлами — `fs.watch` без рекурсии, только раскрытые папки и открытые файлы (300 папок и 200 файлов на реестр, `packages/server/modules/workspace/watcher.ts`).
- Dev-режим тяжелее prod в 7–8 раз по памяти: это цена Vite, native и HMR, а не данных пользователя.
- Окно чата держит последние 5 запросов: 10 000 запросов в истории не отличаются от 10 по цене открытия и потока. Полный монтаж линеен (~3,5 мс и ~77 DOM-узлов на запрос).
- Закрытая «Работа» держит в DOM только заголовок: 200 вызовов — 80 узлов вместо 3 749. Расход перенесён на явное раскрытие.
- Один открытый блок кода в потоке переразбирается каждый раз: обновление растёт линейно с размером блока, весь поток — квадратично. Проза инкрементальна.
- Троттлинг `AgentMarkdown` сохраняет 60 fps и p95 кадра 16,7 мс ценой задержки отдачи.

## Порядок величин

| Показатель                                  | Значение             |
| ------------------------------------------- | -------------------- |
| Prod-сервер в простое                       | ~141–150 МБ RSS      |
| Dev целиком (`vite dev` + native + обёртка) | ~1,1 ГБ              |
| Вкладка в Chromium в простое                | ~55 МБ PSS renderer  |
| Вкладка после 1 млн строк в терминале       | ~121 МБ PSS          |
| Всё приложение в простое (сервер + вкладка) | ~220 МБ              |
| Один проект на сервере                      | ~+0,8 МБ             |
| Один проект во вкладке                      | ~+3–7 МБ PSS         |
| Эхо клавиши через сервер                    | p50 1,3 мс           |
| Вывод PTY                                   | 12–34 МБ/с на сессию |
| `/api/health`                               | p50 0,55 мс          |
| Сборка `dist`                               | ~6,3 МБ, 215 файлов  |

Основной расход в нескольких проектах — процессы пользователя (шелл и dev-серверы), а не сервер или вкладка. После пика RSS сервера возвращается с задержкой порядка минуты; это не подтверждённая утечка.

## Как мерить

Чтобы не трогать рабочий инстанс на 4177, запускайте отдельный процесс с изолированными данными. Порт 4190 использовать нельзя: он в блок-листе `fetch`.

```bash
S=$(mktemp -d)
cd <repo>
export XDG_DATA_HOME=$S/data XDG_CONFIG_HOME=$S/data/cfg PROJECTOR_PORT=4213
node packages/server/app/standalone.ts &
curl -s localhost:4213/api/health            # поле "pid"
grep -E 'VmRSS|VmHWM' /proc/<pid>/status
grep -E 'Rss|Pss|Anonymous' /proc/<pid>/smaps_rollup
```

- **HTTP**: последовательные `fetch` с прогревом, затем перцентили; пропускная способность — 32 параллельных цикла.
- **Терминалы**: `POST /api/projects/<id>/terminals` `{"program":"shell"}` с заголовком `Origin`, затем WebSocket `/api/terminal/socket?session=<id>`; клиент подтверждает каждый `output` сообщением `{"type":"ack","length":N}`.
- **Клиент**: `performance.getEntriesByType('navigation')`, `performance.memory`, подсчёт DOM-узлов.
- **Память**: `process.memoryUsage()` и `v8.getHeapSpaceStatistics()`; состав RSS — `/proc/<pid>/smaps_rollup`.
- **Чат**: `vp run bench:chat` — сценарии и метод в [`scripts/bench-chat`](../scripts/bench-chat/README.md).

Подводные камни:

- Не используйте `pkill -f`/`pgrep -f` с именем скрипта в той же оболочке: совпадёт и она сама.
- После прогона закрывайте сессии (`DELETE` требует `confirmation` из `GET` сессии) или перезапускайте сервер: сессии живут в процессе.
- Не совмещайте замер памяти до и после нагрузки в одном процессе, если нужен «чистый простой»: RSS не откатывается сразу.
- Долгие прогоны с HMR проверяйте отдельно: рост памяти в dev обычно связан с Vite и окружением, а не с бизнес-логикой. Регрессии жизненного цикла: `tests/runtime-lifecycle.test.mjs`, `tests/instance-exit.test.mjs`, `tests/window-host-lifecycle.test.mjs`, `tests/windows-protocol.test.mjs`, `tests/restart.test.mjs`, `tests/environment-runtime.test.mjs`.

## Что не покрыто

Реальные большие репозитории (monorepo, `node_modules`, 100k+ файлов), типовые dev-инструменты внутри терминалов, длительная работа с периодическим снятием памяти, Docker/devcontainer под нагрузкой, LAN с несколькими клиентами и строгое сравнение с VS Code на том же железе.
