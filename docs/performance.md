# Производительность: замер потребления памяти и скорости

Базовый замер, чтобы понимать порядок величин и сравнивать с ним будущие изменения.

|             |                                                                                  |
| ----------- | -------------------------------------------------------------------------------- |
| Дата замера | 2026-10-17 (сервер, терминалы); 2026-10-18 (вкладка в Chromium)                  |
| Версия      | Projector 0.6.0 (коммит `af06f39`)                                               |
| Режим       | **prod** (`server/app/standalone.ts` по собранному `dist`), если не сказано иное |
| Браузер     | Chromium 154, чистый профиль, без расширений (для замера вкладки)                |
| Машина      | Linux 7.2 (Arch), 24 логических ядра, 48 ГБ RAM, KDE/X11                         |
| Рантайм     | Node 24.21.0 (сервер, `.node-version`); клиентский скрипт — Node 24.22.0         |
| Данные      | чистый `XDG_DATA_HOME`, один проект с пустым git-репозиторием и одним файлом     |

Это замер одной машины на localhost, один прогон, без усреднения. Относитесь к цифрам как к порядкам величин, а не к точным значениям.

## Итоги

- Prod-сервер в простое занимает **~141–150 МБ RSS**, из них **~58 МБ** — общие страницы самого бинарника Node, **~92 МБ** — собственная (анонимная) память.
- Один терминал почти ничего не добавляет серверу (**~0,1 МБ**); основная цена — процесс шелла (**~7,5 МБ** на сессию). 24 терминала (лимит) вместе с шеллами: **~400 МБ**.
- После пика нагрузки RSS сервера **не возвращается** (456 МБ после ~100 МБ вывода в PTY, через 25 с после закрытия всех сессий — те же 456 МБ). Это поведение аллокатора и V8; утечкой не подтверждено.
- Задержки HTTP и терминала на localhost малы (доли миллисекунды — единицы миллисекунд). Узкое место вывода терминала — один поток сервера (100% одного ядра), **12–33 МБ/с** на сессию.
- Вкладка в чистом Chromium: renderer **~55 МБ PSS** в простое (~121 МБ после 1 млн строк в терминале), плюс ~13 МБ в GPU/браузерных процессах. Всё приложение целиком (сервер + вкладка): **~220 МБ в простое**, порядка **600 МБ** под тяжёлой нагрузкой; шеллы сверху.
- Сравнение с VS Code (данные из сети, не на этой машине): ~400–900 МБ в простое, 0,8–1 ГБ с открытыми файлами; эхо терминала 62 мс на macOS (VS Code 1.68) против 1,3 мс серверной части Projector. Сравнение корректно при сопоставлении всего стека Projector (сервер + вкладка), так как убранные возможности — осознанный отказ ради производительности. Для строгого вывода нужен замер VS Code на этом же железе.
- Dev-режим (`vp dev`) тяжелее prod в 7–8 раз по памяти (~1,1 ГБ суммарно против ~150 МБ); под нагрузкой не мерился.

## Память

### Сервер: масштабирование

| Состояние                                 | RSS сервера                                                               |
| ----------------------------------------- | ------------------------------------------------------------------------- |
| Старт, простой                            | 141–150 МБ                                                                |
| После HTTP-нагрузки (3000–7900 req/s)     | 212–227 МБ                                                                |
| + 1 / 5 / 10 / 20 / 24 терминала, молчат  | 212,5 / 212,6 / 212,7 / 212,8 / 212,9 МБ (прирост +0,3…+2,3 МБ на все 24) |
| 24 терминала с шеллами (дерево процессов) | 220 / 250 / 288 / 363 / 393 МБ                                            |
| Пик после ~100 МБ вывода в PTY            | 456–470 МБ                                                                |
| После закрытия всех сессий (+25 с)        | 456–470 МБ, дочерних процессов 0                                          |

Рост 141 → 212 МБ после HTTP-нагрузки — рост кучи V8 и буферов, а не терминалов.

### Состав RSS в простое (~150 МБ)

Источник: `/proc/<pid>/smaps_rollup`, `v8.getHeapSpaceStatistics()`.

| Часть                                            | МБ                    | Комментарий                                                                             |
| ------------------------------------------------ | --------------------- | --------------------------------------------------------------------------------------- |
| Бинарник Node и системные библиотеки (`RssFile`) | ~58                   | Файловые страницы, общие между процессами. Пустой `node -e` — ~43 МБ.                   |
| Куча V8                                          | ~62 всего, ~37 занято | `new_space` 32 (занято ~8), `old_space` 19, `large_object_space` 6, `trusted_space` 3,4 |
| `external` (буферы, строки вне кучи)             | ~14                   |                                                                                         |
| malloc (`[heap]`)                                | ~22                   | Аллокатор C++: node, libuv, node-pty                                                    |
| Прочее анонимное                                 | ~10                   | Стеки 11 потоков и др.                                                                  |

Прирост кучи по модулям при загрузке (порядок импортов искажает цифры, часть пакетов в измерении не нашлась, значения оценочные): `server/app/api.ts` с зависимостями +13 МБ, `plugin.ts` +8 МБ, `os` +6 МБ, агентский модуль +4 МБ, терминалы +2 МБ.

Нативные библиотеки (`pty.node`, GTK-слои в серверном процессе) заметной доли RSS не дают.

Возможные сокращения (оценка, не проверялась как изменение продукта):

- `--max-semi-space-size=2`: RSS 150 → 141 МБ (проверен только запуск и простой).
- Ленивая загрузка тяжёлых модулей (агенты, Docker, devcontainers, провайдеры), пока они не нужны: потенциально 15–25 МБ кучи.

### Клиент (вкладка браузера)

Проект открыт без файлов и терминалов: JS-куча 22,5 МБ (total 28,5), 372 DOM-узла, 33 ресурса, 1,9 МБ трафика; DOMContentLoaded 169 мс, load 286 мс. FCP = 4,9 с — замер сомнителен (вкладка создана автоматически, могла быть в фоне), перемерить в обычном окне. Память процессов Chromium — в подразделе ниже.

#### Вкладка в чистом Chromium (дополнение, 2026-10-18)

Чтобы считать вклад именно вкладки, а не весь браузер: Chromium 154 с чистым профилем (`--user-data-dir`, без расширений), перед Projector открыты три фоновые вкладки на других хостах. Память процесса считалась по PSS (доля общих страниц делится между процессами) и RSS. Renderer вкладки определялся как процесс с наибольшим приростом PSS: страница попадает в уже запущенный spare-renderer, так что «новый PID» не годится.

| Состояние                               | renderer вкладки PSS / RSS | JS-куча (used) | DOM |
| --------------------------------------- | -------------------------- | -------------- | --- |
| Проект открыт, 0 терминалов             | 54,8 / 173,6 МБ            | 9,1 МБ         | 362 |
| 5 терминалов в проекте                  | 59,0 / 179,8 МБ            | 11,3 МБ        | 484 |
| 10 терминалов в проекте                 | 56,8 / 177,1 МБ            | 11,5 МБ        | 514 |
| После 1 млн строк (~6,9 МБ) в терминале | 121,1 / 241,7 МБ           | 17,5 МБ        | 546 |

- Приватная (анонимная) часть renderer при открытии: ~40 МБ. Остальное в RSS — общие страницы Chromium.
- Открытие Projector добавило ещё ~13 МБ PSS в GPU-процессе и процессах браузера.
- Фоновые пустые вкладки: ~15 МБ PSS на renderer.
- Рост после большого вывода — scrollback xterm.js (по умолчанию тысячи строк с атрибутами) и буферы. Верхней границы я не искал.
- Всё приложение целиком в простое: сервер ~150 + вкладка ~55 + GPU/браузер ~13 ≈ **220 МБ**. Под нагрузкой (после вывода ~100 МБ в PTY на сервере и 1 млн строк во вкладке) — порядка 600 МБ. Шеллы (~7,5 МБ каждый) сверху.
- Ограничения: один прогон, окно Chromium обычное (не headless), вывод шёл в терминал, который мог быть не отображён во вкладке; при сомнениях перемерить с видимым терминалом. Скрипт замера (`tab.mjs`) в репозиторий не включён.

### Dev-режим (одна точка, `ps`, без нагрузки)

Через 80 с после старта: `vite dev` ~726 МБ, native (GTK) ~281 МБ, обёртка `vp dev` ~112 МБ. Итого ~1,1 ГБ.

| `/api/health`               | 0,55 мс    | 0,78 мс    | 1,3 мс |

## Ограничения

- `MAX_SESSIONS = 24` терминальных сессий (`server/modules/terminal/session-state.ts:17`); 25-я возвращает «Лимит терминалов».
- Сервер однопоточен для ввода-вывода: вывод PTY, снимки экрана (`@xterm/headless`) и HTTP делят одно ядро.
- Не измерялось: большие проекты (деревья файлов, поиск, git на больших репозиториях), агентные чаты, Docker/devcontainer, режим локальной сети с несколькими клиентами, длительная работа (дрейф памяти), dev-режим под нагрузкой.

## Методология

Чтобы не трогать рабочий инстанс на 4177, замер идёт в отдельном процессе с изолированными данными. Порт 4190 использовать нельзя: он в блок-листе `fetch` (ошибка `bad port`). Подходят, например, 4213. Клиент ходит на `localhost`, не на `127.0.0.1`: сервер слушает `localhost`.

```bash
S=$(mktemp -d)
cd <repo>
export XDG_DATA_HOME=$S/data XDG_CONFIG_HOME=$S/data/cfg PROJECTOR_PORT=4213
node server/app/standalone.ts &        # prod; мерить RSS по PID из /api/health
# PID, память
curl -s localhost:4213/api/health      # поле "pid"
grep -E 'VmRSS|VmHWM' /proc/<pid>/status
grep -E 'Rss|Pss|Anonymous' /proc/<pid>/smaps_rollup
```

- **RSS** брался из `/proc/<pid>/status`, суммарное по дереву — обходом `/proc/*/stat` по PPid.
- **HTTP**: последовательные `fetch` с прогревом 50 запросов, затем перцентили; пропускная способность — 32 параллельных цикла `fetch` по 4 с, CPU сервера из `utime+stime` в `/proc/<pid>/stat`.
- **Терминалы**: `POST /api/projects/<id>/terminals` `{"program":"shell"}` (заголовок `Origin` = адрес сервера обязателен), затем WebSocket `/api/terminal/socket?session=<id>`; клиент подтверждает каждый `output` сообщением `{"type":"ack","length":N}`, ввод — `{"type":"input","data":…}`. Завершение вывода определялось по маркеру (`echo DONE_$((1+1))`), не по приглашению шелла.
- **Состав RSS**: `--import` с таймером, печатающим `process.memoryUsage()` и `v8.getHeapSpaceStatistics()`; флаги V8 проверялись перезапуском.
- **Клиент**: `performance.getEntriesByType('navigation')`, `performance.memory`, подсчёт DOM-узлов в открытом проекте.
- Скрипты замера лежали во временном каталоге и в репозиторий не включены.

Подводные камни:

- Не используйте `pkill -f`/`pgrep -f` с именем скрипта в той же оболочке: совпадёт и она сама.
- После каждого прогона закрывайте сессии (`DELETE` требует `confirmation` из `GET` сессии) или перезапускайте сервер: сессии живут в процессе.
- Не совмещайте замер памяти до и после нагрузки в одном процессе, если нужен «чистый простой»: RSS не откатывается.

## Что перемерить при следующем замере

1. Тот же набор в dev-режиме отдельным процессом.
2. Большой проект (≥100 тыс. файлов): дерево, поиск (`rg`), git-статус.
3. Долгий прогон (часы) с периодическим снятием RSS — проверка на утечки.
4. Браузерная часть в реальном окне: FCP/LCP, рендер терминала, память вкладки через Process Explorer Chrome.
5. Эффект `--max-semi-space-size=2` и ленивой загрузки модулей на RSS и на пропускную способность.
