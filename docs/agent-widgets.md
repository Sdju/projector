# Компоненты в ответах агента

Ответ штатного ассистента может содержать Vue-компоненты прямо в markdown: показатели, графики, колонки, вкладки, формы выбора. Агент пишет блок с новой строки (`<Stat label="…" value="…" />`), клиент рисует его настоящим компонентом. Внутри блока Markdown не рендерится: `**`, обратные кавычки, списки, `###` и таблицы остаются сырым текстом, поэтому содержимое пишется валидным HTML (`<strong>`, `<code>`, `<ul><li>`, `<h3>`, `<table>`). Это правило входит в постоянную справку агента.

## Где что лежит

Виджеты — масштабируемая сущность, поэтому они регистрируются через сквозной модуль (контейнер) в `packages/core` и `packages/client`, по образцу `agents-integration` ([архитектура](architecture.md)):

| Место                                                              | Что                                                                                                                                           |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/core/modules/widget-catalog`                             | Контракт `WidgetDefinition` и каталог: из определений собирает инструкцию агенту (`guide()`) и справку по компоненту (`describe(name)`)       |
| `packages/core/modules/agent-widgets/<имя>/index.ts`               | Определение виджета: имя, группа, описание, свойства с типами, `v-model`, примечания, `special`, пример. Без Vue                              |
| `packages/client/modules/agent-widgets/<имя>/`                     | Реализация: `ui/<Имя>.vue` и `index.ts`, который отдаёт `{ definition, component }`. Общее ядро контейнера (`_/`) — контексты формы и вкладок |
| `packages/client/modules/widget-runtime`                           | Реестр (`registerWidget`), разбор сообщения, автозакрытие, компиляция, хост компонента, общий контекст ответа, мост `reply`                   |
| `packages/server/modules/project-widgets`                          | `.projector/widgets.json`, доверие по хешу, данные виджетов и фильтр для промпта                                                              |
| `packages/client/modules/project-widgets`                          | Настройки проекта: доверие, список виджетов и команды                                                                                         |
| `packages/client/app/widgets.ts`, `packages/server/app/widgets.ts` | Единственные места, где встроенные виджеты названы: клиент регистрирует определение с компонентом, сервер — определение для промпта           |

Чат не знает ни одного встроенного виджета, а промпт ассистента не содержит их описаний: текст возможности `widgets` (`packages/server/app/features.ts`) берётся из зарегистрированных определений (`widgetCatalog.guide()`), поэтому он не расходится с тем, что клиент умеет рисовать. Проектные виджеты добавляются к этой справке только для своего проекта и только после доверия. Эту возможность можно включить и другим агентам — см. [возможности агентов](agent-features.md). Справка разделяет метаданные и Vue-разметку: типы и обязательность свойств описаны текстом, рядом приведён рабочий пример каждого компонента. Условные обозначения необязательности не вставляются в теги. Тест сверяет определения, свойства компонентов (`defineProps`) и оба списка регистрации.

### Специальные виджеты

Флаг `special: true` не меняет рендеринг: компонент по-прежнему доступен в ответе. Он регулирует только объём постоянного промпта. Обычные виджеты попадают в справку целиком; специальные — одной строкой `Имя — когда использовать` в разделе «Специальные виджеты». Их свойства, примечания и пример выдаёт инструмент `describe_widget` (`widgetCatalog.describeSpecial(name)`), который агент вызывает перед первым использованием.

Так добавляют редкие, но полезные компоненты со сложной схемой. Сейчас так зарегистрирован `GitInfo`: он показывает ветку и upstream, ahead/behind, состояние рабочего дерева, diff и последние коммиты по переданным агентом данным. Остальные новые data-виджеты — `Image`, `InlineIcon` и `Chips` — обычные и описаны в промпте полностью. `Chips` принимает строки или `{ label, tone, icon }`: шесть смысловых тонов и иконки из общего набора; без тона метки получают чередующиеся цвета. `Image` понимает те же источники, что markdown-картинка `![alt](путь)`: путь файла проекта, абсолютный путь на диске (`/tmp/...`, `file://`, `C:\...`), внешний URL и `data:`. Разрешение пути живёт в модуле `chat-images`, поэтому markdown и виджет не расходятся; клик открывает тот же просмотр с масштабом, а сбой загрузки оставляет ссылку с alt.

`SafeSecretShow` — специальный виджет для уже существующего секрета: агент пишет `script` (shell-команда, чей stdout — ключ или токен), `label` и `comment`, а значение получает только браузер пользователя. Скрипт запускается на сервере по нажатию «Показать секрет»; команда видна под кнопкой. Секрет не попадает ни в ответ, ни в историю чата, ни в контекст модели, а панель умеет скрыть и скопировать значение. Для агентов с MCP-сервером `projector-ide` тот же сценарий доступен инструментом `show_secret`: он запускает скрипт в процессе MCP и показывает панель через `POST /api/agent/secret-show/push`; агенту возвращается только `{ shown, delivered }`. Скрипт в `show_secret` штатного Projector проходит ту же проверку, что `bash`; виджет всегда ждёт явного нажатия.

### Как добавить виджет

1. `packages/core/modules/agent-widgets/<имя>/index.ts`: `defineWidget({ name, group, summary, props, model?, notes?, special?, example })`. Описание — это то, что прочитает агент: когда виджет нужен, что значит каждое свойство, какие у него неочевидные правила. Для редкого сложного виджета поставьте `special: true` и сформулируйте `summary` как условие использования.
2. `packages/client/modules/agent-widgets/<имя>/ui/<Имя>.vue` и `index.ts` с `WidgetEntry`.
3. Добавьте виджет в `packages/client/app/widgets.ts` и `packages/server/app/widgets.ts`.
4. `vp test run tests/agent-widgets.test.mjs`: тест проверит, что свойства определения совпадают со свойствами компонента.

## Виджеты проекта

Проект может объявить свои компоненты в `.projector/widgets.json`. Это не полноценные Vue-файлы: шаблон собирается из уже зарегистрированных виджетов, обычного HTML/SVG и CSS, а импорты запрещены. Логика живёт в отдельном поле `script`; `<script>` внутри `template` по-прежнему не принимается. Так проект получает специфичные карточки, таблицы метрик или формы без собственной сборки.

```json
{
  "version": 1,
  "widgets": [
    {
      "name": "ModelMetrics",
      "summary": "метрики выбранной модели: скорость и качество",
      "special": true,
      "props": {
        "model": { "type": "string", "description": "имя модели", "required": true }
      },
      "data": { "metrics": "reports/metrics.json" },
      "refresh": 30,
      "script": "const speed = computed(() => data.metrics.speed); return { speed };",
      "styles": ".row { gap: 8px }",
      "template": "<Card :title=\"model\"><Row class=\"row\"><Stat label=\"Скорость\" :value=\"speed\" /></Row></Card>",
      "example": "<ModelMetrics model=\"gpt-5\" />"
    }
  ]
}
```

- **Имя** — PascalCase. Встроенные имена (`Stat`, `Card`, `IntelligentForm` и другие) заняты; шаблон может ссылаться на встроенные виджеты и на соседние проектные виджеты.
- **`special`** оставляет в постоянном промпте только имя и условие использования; свойства и пример выдаёт `describe_widget`. Без флага описание попадает в промпт целиком.
- **`props`** — свойства компонента. Поддерживаются `string`, `number`, `boolean`, `array`, `object` и их объединения через `|`. Значения приходят из ответа агента.
- **`data`** — карта «переменная → JSON-файл проекта». Значения доступны в шаблоне как `data.metrics`; секретные пути, выход за проект и файлы больше 1 МБ отклоняются. `refresh` (не меньше 5 секунд) перечитывает данные, пока виджет на экране.
- **`script`** — тело функции, которая выполняется один раз после первой загрузки данных. В нём доступны `ref`, `reactive`, `computed`, `watch`, `onMounted`, `reply`, `props`, `data`, `dataErrors`, `dataLoading` и `dataError`; `return { … }` добавляет значения в шаблон. Скрипт видит `data.metrics` уже загруженным, а изменения ref/computed сразу обновляют шаблон. `<script>` внутри `template` не исполняется: скрипт задаётся только этим полем.
- **`styles`** — CSS, который автоматически ограничивается обёрткой виджета. `@keyframes`, `@font-face` и вложенные `@media` поддерживаются; глобальные селекторы не утекают в остальной интерфейс.
- **`answer: true`** разрешает виджету быть формой следующего ответа, если в его шаблоне есть `IntelligentForm` или `Form`. Композер и снимок хранят тот же тег; данные формы восстанавливаются как у встроенных форм.
- **Данные передаёт агент** через props или проект через `data`. `script` не ограничен песочницей: после доверия он исполняется в интерфейсе Projector и видит браузерные API. Доверяйте только проверенному файлу.

Файл **не действует без доверия**. Доверие выдаётся на странице настроек проекта, в разделе «Виджеты проекта», и привязано к хешу файла; любая правка отзывает его. Недоверенный файл не попадает ни в промпт, ни в реестр клиента, и его `script` не выполняется. Доверие хранится в `$XDG_DATA_HOME/projector/agent/widget-trust.json`.

Доставка повторяет возможности агентов:

- Projector получает справку проекта в системный промпт, Claude Code — в `systemPrompt.append`, ACP-агенты — в первое сообщение;
- `describe_widget` Projector и MCP-сервер `projector-widgets` читают те же доверенные определения;
- клиент держит отдельный реестр на `projectId`, поэтому одинаковые имена в разных проектах не конфликтуют; после загрузки определения открытый чат перерисовывает сообщения без перезагрузки.

API: `GET /api/agent/project-widgets?projectId=`, `PUT /api/agent/project-widgets/trust` `{ projectId, trusted }`, `GET /api/agent/project-widgets/data?projectId=&widget=`. Команды настроек проекта — `ide.project.widgets.list` и `ide.project.widgets.trust`.

Ограничения: правка файла влияет на новые и повторно открытые ответы; уже смонтированный ответ сохраняет прежнее определение до перезагрузки; MCP-процесс читает определения при старте сессии; формы проекта не проходят Form Doctor для внутренней ошибки шаблона — невалидное определение видно в настройках и в ответе как ошибка виджета.

## Field и бюджет справки

Поля формы сведены в один виджет `Field` с полем `type` (по умолчанию `text`): `text`, `textarea`, `number`, `slider`, `select`, `radio`, `checks`, `switch`, `date`, `time` или `segmented`. Общие свойства — `name`, `label`, `hint`, `initial`, `placeholder`, `required`, `disabled`; `options` нужен для `select`/`radio`/`checks`, `min`/`max`/`step`/`unit` — для `number`/`slider`, `rows` — для `textarea`. `required` проверяется при отправке формы: ошибка показывается у поля, а ответ не уходит, пока поле не заполнено. `checks` возвращает массив, `switch` — boolean, числовые типы — number, остальные — string.

Старые `Input`, `Checks` и `Slider` остаются зарегистрированными только для старых ответов: в `guide()` они скрыты (`hidden: true`), но `describe_widget` и рендер по-прежнему работают. Это позволяет не ломать историю и не тратить постоянный промпт на три legacy-определения. Для виджетов с большой матрицей свойств можно задать компактный `guide`, а полные `props`/`notes` оставить для `describe_widget`.

Размер постоянной справки — часть контракта: тест `tests/agent-widgets.test.mjs` держит `widgetCatalog.guide()` ниже 9 500 символов. Сейчас после перевода полей на `Field` и компактных Form/IntelligentForm/Tabs справка занимает около 8,8 тыс. символов вместо прежних 11,6 тыс.

## Как рендерится

- **Разбор** (`split.ts`). Блок — строка, начинающаяся с `<PascalCase`, чьё имя есть в реестре, вне кода. Всё остальное — markdown с обычным HTML (`html: true`): DOMPurify оставляет безопасную разметку, а ссылки и картинки из неё получают те же действия, что markdown-ссылки и `![…](…)`. `<script>` между блоками — отдельная часть; внутри блока — часть блока.
- **Прогрессивность** (`autoclose.ts`). Пока блок пишется, недописанное отбрасывается (тег, который ещё не закрыт, открытое `{{`, комментарий, `<script>`), а каждый открытый элемент закрывается. Получается валидный шаблон, который растёт элемент за элементом.
- **Без пересоздания** (`host.ts`, `ui/AgentWidget.vue`). Виджет монтируется одним компонентом на всю жизнь. Состояние скрипта создаётся один раз, меняется только функция рендера (не чаще раза за кадр; одинаковый текст шаблона компилируется один раз). Поэтому DOM, введённый текст, ползунок и вкладка переживают каждый чанк. Если новый текст не продолжает прежний, хост создаётся заново.
- **Почему это работает.** Скомпилированный шаблон помечает слоты стабильными и строит блоки с перечнем динамических потомков; Vue верит этому и не обновляет то, что «не менялось». Для одного шаблона это верно, для подмены шаблонов нет. Рендер хоста и отложенное выполнение слотов идут без отслеживания блоков (`setBlockTracking`), а флаг стабильных слотов заменён на динамический (`compile.ts`), и Vue делает полный diff. Отключение отслеживания внутри слотов необходимо и для статического SVG: иначе после стриминга остаётся ранняя пустая версия дерева.
- **Терпимость.** Пока сообщение не закончилось, имя, которого ещё нет, читается как пустое, ошибка дочернего компонента гасится, а виджет `inert` (недописанную форму нельзя отправить). Когда ответ завершён, неизвестное имя или исключение показываются как ошибка с исходником.
- **Компилятор.** `@vue/compiler-dom` загружается лениво при первом блоке.

## Скрипты и данные

- `<script>` внутри блока видит только этот блок. Между блоками `<script>` один на весь ответ: его значения видны во всех блоках (ползунок в одном управляет графиком в другом), порядок не важен. В скрипте доступны `ref`, `reactive`, `computed`, `watch`, `onMounted`, `reply`; он заканчивается `return { … }`. Исполнение кода не ограничено.
- Блок, которому не хватило имени из скрипта, пришедшего позже, пробует снова после выполнения скрипта.

## Ответ агенту

`reply(данные, "подпись")` отправляет в чат сообщение пользователя: подпись и данные в JSON. Отправка только по клику: `reply` проверяет `navigator.userActivation`, поэтому `onMounted`, `watch` и программный `.click()` в скрипте ничего не отправят. `<Form>` с полями `name` и кнопкой `<Button submit>` делает то же без скрипта: после отправки форма блокируется.

## Форма вместо поля ввода

Предпочтительный способ — ответ, который заканчивается `<IntelligentForm>`: внутрь кладутся поля `Checks`, `Input`, `Slider` и `Tabs` с `name`. Не нужно оборачивать форму в `<Card>` или `<Form>` и добавлять `<Button submit>`: в поле ввода форму отправляет общая кнопка композера, а `summary` задаёт подпись ответа. Собственная кнопка формы (`submit`, `sentLabel`) нужна только в сообщении и readonly-снимке, где композера рядом нет. Если ответ заканчивается этим блоком, композер показывает его вместо текстового поля; кнопка-иконка в нижней панели возвращает обычный ввод и обратно. Активная `<IntelligentForm>` не дублируется в ответе — она остаётся только в поле ввода; после отправки её копия в ответе тоже скрывается, потому что readonly-снимок с выбранными значениями уже стоит в сообщении пользователя. Карандаш у снимка снимает блокировку для нового ответа.

Старая разметка `<Form>` с `<Button submit>` продолжает работать, в том числе внутри `<Card>`; у неё в ответе остаётся короткая строка «Форма доступна в поле ввода». Выбор блока живёт в `packages/client/modules/widget-runtime/answer.ts`, снимок и отправка — в `packages/client/modules/agent/model/answer-form.ts`, панель композера — в `packages/client/modules/agent-turns/ui/AgentFormPanel.vue`, readonly-снимок и inline-правка — в `packages/client/modules/agent-turns/ui/AgentFormAnswer.vue`.

Ограничения формы:

- ответ должен заканчиваться формой: текст после неё выключает режим, а из нескольких форм берётся последняя;
- форма самодостаточна: общий `<script>` между блоками ответа в композер и снимок не переносится, поэтому значения задаются литералами свойств или `<script>` внутри блока;
- отказ от формы («Текст») не запоминается между перезагрузками: при следующем открытии чата форма снова станет полем ввода, пока на неё не ответят;
- старые формы в предыдущих ответах не создают снимок при клике: снимок делают композер и карандаш у уже отправленного сообщения;
- `<Button send>` без `<Form>` отправит значение, но снимок покажет только саму кнопку: полей, в которых было бы видно отправленное, у такой панели нет.

### Form Doctor

Ответ с формой не показывается с ошибкой компилятора. Сначала `packages/client/modules/widget-runtime/repair.ts` пытается исправить разметку без модели: убирает повторяющиеся атрибуты, закрывает незавершённые теги и проверяет результат через Vue-компилятор. Если форма всё ещё невалидна, клиент отправляет историю, форму и текст ошибки в `POST /api/agent/form-repair`; модель роли `doctor` (по умолчанию — модель чата) переписывает блок, после чего он снова проходит проверку. Попыток не больше трёх; исходная форма остаётся в ответе, а в композер попадает проверенный вариант. Если восстановить не удалось, остаётся обычное текстовое поле — техническая ошибка не выводится в чат.

### Answer Doctor

После завершения ответа клиент проверяет Vue-разметку всех виджетов и ищет Markdown, который попал внутрь виджета и поэтому показывается как сырой текст. Обычный Markdown вне виджетов проверку не запускает. При проблеме `POST /api/agent/answer-repair` передаёт модели роли `doctor` (по умолчанию — модели чата) историю, ответ и диагностику; модель возвращает весь ответ с HTML вместо Markdown внутри виджетов. Результат снова проверяется, попыток не больше трёх. Проверенный ответ заменяет текст и текстовые части исходного turn и сохраняется через общий `persist()` чата, поэтому после перезагрузки doctor не запускается повторно. Если восстановление не удалось, остаётся исходный ответ.

Работа doctor видна в ряду действий под ответом. Пока он переписывает разметку, там пульсирует значок стетоскопа; после исправления он остаётся зелёным, а при неудаче — красным. Подписей в чате нет: наведение или фокус на значке открывают тултип с первой диагностикой, результатом последней проверки, числом попыток и затраченным временем. Красный значок можно нажать, чтобы запустить новую попытку. Итог сохраняется в поле `doctor` turn вместе с FNV-хешем исправленного текста: значок остаётся после перезагрузки, а новый ответ после повтора или правки его скрывает. Если doctor не справился за три попытки, значок предупреждает об этом, а в чате остаётся исходный ответ. Устаревшая неудача снимается сама, когда повторная проверка больше не находит проблемы.

Проверка не принимает `<` внутри значений атрибутов за компонент и смотрит Markdown только в текстовых узлах: содержимое `code`, `pre`, `script` и `style` не считается, а теги не превращаются в переводы строк. Поэтому `<Module>` в строке `:items` и знаки `+` между `<code>` больше не запускают doctor.

`tests/agent-widgets.test.mjs` (разбор, автозакрытие на каждом префиксе, каталог, бюджет справки, скрытые legacy-поля, сверка наборов, выбор `<IntelligentForm>`), `tests/project-widgets.test.mjs` (нормализация, отдельное поле `script`, доверие по хешу, данные, симлинк и секреты, справка проекта), `tests/project-widgets-api.test.mjs` (API доверия и данных) и `tests/agent-widgets-browser.test.mjs` (реальный Chromium: стриминг без пересоздания узлов, отсутствие ошибок на каждом шаге, одно выполнение скрипта, проектный скрипт с данными, `Field` со всеми основными типами, формы, лейауты, общий контекст).
