# Компоненты в ответах агента

Ответ штатного ассистента может содержать Vue-компоненты прямо в markdown: показатели, графики, колонки, вкладки, формы выбора. Агент пишет блок с новой строки (`<Stat label="…" value="…" />`), клиент рисует его настоящим компонентом.

## Где что лежит

Виджеты — масштабируемая сущность, поэтому они регистрируются через сквозной модуль (контейнер) в `packages/core` и `packages/client`, по образцу `agents-integration` ([архитектура](architecture.md)):

| Место                                                              | Что                                                                                                                                           |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/core/modules/widget-catalog`                             | Контракт `WidgetDefinition` и каталог: из определений собирает инструкцию агенту (`guide()`) и справку по компоненту (`describe(name)`)       |
| `packages/core/modules/agent-widgets/<имя>/index.ts`               | Определение виджета: имя, группа, описание, свойства с типами, `v-model`, примечания, `special`, пример. Без Vue                              |
| `packages/client/modules/agent-widgets/<имя>/`                     | Реализация: `ui/<Имя>.vue` и `index.ts`, который отдаёт `{ definition, component }`. Общее ядро контейнера (`_/`) — контексты формы и вкладок |
| `packages/client/modules/widget-runtime`                           | Реестр (`registerWidget`), разбор сообщения, автозакрытие, компиляция, хост компонента, общий контекст ответа, мост `reply`                   |
| `packages/client/app/widgets.ts`, `packages/server/app/widgets.ts` | Единственные места, где виджеты названы: клиент регистрирует определение с компонентом, сервер — определение для промпта ассистента           |

Чат не знает ни одного виджета, а промпт ассистента не содержит их описаний: текст возможности `widgets` (`packages/server/app/features.ts`) берётся из зарегистрированных определений (`widgetCatalog.guide()`), поэтому он не расходится с тем, что клиент умеет рисовать. Эту возможность можно включить и другим агентам — см. [возможности агентов](agent-features.md). Справка разделяет метаданные и Vue-разметку: типы и обязательность свойств описаны текстом, рядом приведён рабочий пример каждого компонента. Условные обозначения необязательности не вставляются в теги. Тест сверяет определения, свойства компонентов (`defineProps`) и оба списка регистрации.

### Специальные виджеты

Флаг `special: true` не меняет рендеринг: компонент по-прежнему доступен в ответе. Он регулирует только объём постоянного промпта. Обычные виджеты попадают в справку целиком; специальные — одной строкой `Имя — когда использовать` в разделе «Специальные виджеты». Их свойства, примечания и пример выдаёт инструмент `describe_widget` (`widgetCatalog.describeSpecial(name)`), который агент вызывает перед первым использованием.

Так добавляют редкие, но полезные компоненты со сложной схемой. Сейчас так зарегистрирован `GitInfo`: он показывает ветку и upstream, ahead/behind, состояние рабочего дерева, diff и последние коммиты по переданным агентом данным. Остальные новые data-виджеты — `Image`, `InlineIcon` и `Chips` — обычные и описаны в промпте полностью. `Chips` принимает строки или `{ label, tone, icon }`: шесть смысловых тонов и иконки из общего набора; без тона метки получают чередующиеся цвета. `Image` понимает те же источники, что markdown-картинка `![alt](путь)`: путь файла проекта, абсолютный путь на диске (`/tmp/...`, `file://`, `C:\...`), внешний URL и `data:`. Разрешение пути живёт в модуле `chat-images`, поэтому markdown и виджет не расходятся; клик открывает тот же просмотр с масштабом, а сбой загрузки оставляет ссылку с alt.

### Как добавить виджет

1. `packages/core/modules/agent-widgets/<имя>/index.ts`: `defineWidget({ name, group, summary, props, model?, notes?, special?, example })`. Описание — это то, что прочитает агент: когда виджет нужен, что значит каждое свойство, какие у него неочевидные правила. Для редкого сложного виджета поставьте `special: true` и сформулируйте `summary` как условие использования.
2. `packages/client/modules/agent-widgets/<имя>/ui/<Имя>.vue` и `index.ts` с `WidgetEntry`.
3. Добавьте виджет в `packages/client/app/widgets.ts` и `packages/server/app/widgets.ts`.
4. `vp test run tests/agent-widgets.test.mjs`: тест проверит, что свойства определения совпадают со свойствами компонента.

## Как рендерится

- **Разбор** (`split.ts`). Блок — строка, начинающаяся с `<PascalCase`, чьё имя есть в реестре, вне кода. Всё остальное — markdown (`html: false`, DOMPurify). `<script>` между блоками — отдельная часть; внутри блока — часть блока.
- **Прогрессивность** (`autoclose.ts`). Пока блок пишется, недописанное отбрасывается (тег, который ещё не закрыт, открытое `{{`, комментарий, `<script>`), а каждый открытый элемент закрывается. Получается валидный шаблон, который растёт элемент за элементом.
- **Без пересоздания** (`host.ts`, `ui/AgentWidget.vue`). Виджет монтируется одним компонентом на всю жизнь. Состояние скрипта создаётся один раз, меняется только функция рендера (не чаще раза за кадр; одинаковый текст шаблона компилируется один раз). Поэтому DOM, введённый текст, ползунок и вкладка переживают каждый чанк. Если новый текст не продолжает прежний, хост создаётся заново.
- **Почему это работает.** Скомпилированный шаблон помечает слоты стабильными и строит блоки с перечнем динамических потомков; Vue верит этому и не обновляет то, что «не менялось». Для одного шаблона это верно, для подмены шаблонов нет. Рендер хоста и отложенное выполнение слотов идут без отслеживания блоков (`setBlockTracking`), а флаг стабильных слотов заменён на динамический (`compile.ts`), и Vue делает полный diff. Отключение отслеживания внутри слотов необходимо и для статического SVG: иначе после стриминга остаётся ранняя пустая версия дерева.
- **Терпимость.** Пока сообщение не закончилось, имя, которого ещё нет, читается как пустое, ошибка дочернего компонента гасится, а виджет `inert` (недописанную форму нельзя отправить). Когда ответ завершён, неизвестное имя или исключение показываются как ошибка с исходником.
- **Компилятор.** `@vue/compiler-dom` загружается лениво при первом блоке.

## Скрипты и данные

- `<script>` внутри блока видит только этот блок. Между блоками `<script>` один на весь ответ: его значения видны во всех блоках (ползунок в одном управляет графиком в другом), порядок не важен. В скрипте доступны `ref`, `reactive`, `computed`, `watch`, `onMounted`, `reply`; он заканчивается `return { … }`. Исполнение кода не ограничено.
- Блок, которому не хватило имени из скрипта, пришедшего позже, пробует снова после выполнения скрипта.

## Ответ агенту

`reply(данные, "подпись")` отправляет в чат сообщение пользователя: подпись и данные в JSON. Отправка только по клику: `reply` проверяет `navigator.userActivation`, поэтому `onMounted`, `watch` и программный `.click()` в скрипте ничего не отправят. `<Form>` с полями `name` и кнопкой `<Button submit>` делает то же без скрипта: после отправки форма блокируется.

## Форма вместо поля ввода

Предпочтительный способ — ответ, который заканчивается `<IntelligentForm>`: внутрь кладутся поля `Checks`, `Input`, `Slider` и `Tabs` с `name`. Не нужно оборачивать форму в `<Card>` или `<Form>` и добавлять `<Button submit>`: в поле ввода форму отправляет общая кнопка композера, а `summary` задаёт подпись ответа. Собственная кнопка формы (`submit`, `sentLabel`) нужна только в сообщении и readonly-снимке, где композера рядом нет. Если ответ заканчивается этим блоком, композер показывает его вместо текстового поля; кнопка-иконка в нижней панели возвращает обычный ввод и обратно. Активная `<IntelligentForm>` не дублируется в ответе — она остаётся только в поле ввода; после отправки её копия в ответе тоже скрывается, потому что readonly-снимок с выбранными значениями уже стоит в сообщении пользователя. Карандаш у снимка снимает блокировку для нового ответа.

Старая разметка `<Form>` с `<Button submit>` продолжает работать, в том числе внутри `<Card>`; у неё в ответе остаётся короткая строка «Форма доступна в поле ввода». Выбор блока живёт в `packages/client/modules/widget-runtime/answer.ts`, снимок и отправка — в `packages/client/modules/agent/model/answer-form.ts`, панель композера — в `AgentFormPanel.vue`, readonly-снимок и inline-правка — в `AgentFormAnswer.vue`.

Ограничения формы:

- ответ должен заканчиваться формой: текст после неё выключает режим, а из нескольких форм берётся последняя;
- форма самодостаточна: общий `<script>` между блоками ответа в композер и снимок не переносится, поэтому значения задаются литералами свойств или `<script>` внутри блока;
- отказ от формы («Текст») не запоминается между перезагрузками: при следующем открытии чата форма снова станет полем ввода, пока на неё не ответят;
- старые формы в предыдущих ответах не создают снимок при клике: снимок делают композер и карандаш у уже отправленного сообщения;
- `<Button send>` без `<Form>` отправит значение, но снимок покажет только саму кнопку: полей, в которых было бы видно отправленное, у такой панели нет.

### Form Doctor

Ответ с формой не показывается с ошибкой компилятора. Сначала `packages/client/modules/widget-runtime/repair.ts` пытается исправить разметку без модели: убирает повторяющиеся атрибуты, закрывает незавершённые теги и проверяет результат через Vue-компилятор. Если форма всё ещё невалидна, клиент отправляет историю, форму и текст ошибки в `POST /api/agent/form-repair`; модель роли `doctor` (по умолчанию — модель чата) переписывает блок, после чего он снова проходит проверку. Попыток не больше трёх; исходная форма остаётся в ответе, а в композер попадает проверенный вариант. Если восстановить не удалось, остаётся обычное текстовое поле — техническая ошибка не выводится в чат.

### Answer Doctor

После завершения ответа клиент проверяет Vue-разметку всех виджетов и ищет Markdown, который попал внутрь виджета и поэтому показывается как сырой текст. Обычный Markdown вне виджетов проверку не запускает. При проблеме `POST /api/agent/answer-repair` передаёт модели роли `doctor` (по умолчанию — модели чата) историю, ответ и диагностику; модель возвращает весь ответ с HTML вместо Markdown внутри виджетов. Результат снова проверяется, попыток не больше трёх. Проверенный ответ заменяет текст и текстовые части исходного turn и сохраняется через общий `persist()` чата, поэтому после перезагрузки doctor не запускается повторно. Если восстановление не удалось, остаётся исходный ответ.
