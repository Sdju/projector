# Архитектура Projector

Projector использует FEOD для всех приложений и собственной библиотеки renderer. Политика задана в `feod.config.mjs` (см. «Проверка границ»). Тонкий клиентский слой `common` содержит только универсальные однофайловые сущности: без бизнес-зависимостей и общих `index.ts`.

| Корень                          | Слои и назначение                                                                                                                                                                                                                                                                       |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src`                           | `app` — Vue bootstrap, router, layouts, assets; `pages` — URL; `modules` — функциональность; `common` — универсальные UI/утилиты; `globals` — ambient declarations                                                                                                                      |
| `server`                        | `app` — Vite plugin и композиция HTTP; `routes` — обработчики по URL; `middlewares` — ограничения локального доступа; `modules` — серверная логика                                                                                                                                      |
| `native`                        | `app` — Node CLI; `modules/desktop` — Vue/GTK-палитра и её контроллер; системные операции — через `core/modules/os`                                                                                                                                                                     |
| `core`                          | Независимые именованные модули: контракты (`launcher`, `project`, `terminal`, `workspace`, `directories`, `ide`, `environment`, `docker`, `devcontainer`, `github`, `agents-integration`), `file-icons`, `editor-themes`, `network-mode`, `server-mode` и Node-модули `app-paths`, `os` |
| `cli`                           | `app` — запуск, перезапуск, desktop installation, импорт ключа                                                                                                                                                                                                                          |
| `packages/vio/examples/counter` | `app` — bootstrap GTK demo; `modules/counter` — компонент примера                                                                                                                                                                                                                       |
| `packages/vio/src`              | `app` — публичная композиция библиотеки; `modules` — renderer, GTK driver/components, SFC compiler, loader                                                                                                                                                                              |

Слой `app` собирает приложение. Модули не импортируют `app`, страницы, маршруты или middleware. Страницы независимы друг от друга; маршруты и middleware также независимы. HTTP dispatcher находится в `server/app/api.ts` и связывает их. Имена страниц соответствуют маршрутам: `/` → `pages/index.vue`, `/projects/<путь>` → `pages/projects/[...projectPath].vue`, `/gh/projects/owner/repository` → `pages/gh/projects/[...githubPath].vue`, `/settings` → `pages/settings.vue`.

Внешние потребители модуля импортируют только его `index.ts`. Реализация остаётся приватной. Подмодуль может использовать реализацию родителя; родитель обращается к непосредственному подмодулю через его публичный API. Вложенные подмодули недоступны соседним модулям. Циклы зависимостей запрещены, включая зависимости типов.

## Сквозные модули

Сквозной модуль — контейнер публичных адаптеров с приватным общим ядром. Он объявляется через `transitModules` в настройках конкретного корня `feod.config.mjs`. У контейнера нет собственного `index.ts` или файлов реализации: непосредственные подмодули располагаются без промежуточной папки `modules/`, каждый имеет свой `index.ts`. Внешний код и соседние адаптеры обращаются к ним через эти публичные входы. Обычная вложенность `modules/` внутри адаптеров сохраняет прежние ограничения.

Интеграции Codex, Claude Code, OpenCode и Cursor находятся в `modules/agents-integration` трёх корней:

```text
src/modules/agents-integration/
  _/                 # приватные polling и UsageMeter
  codex/index.ts     # индикатор Codex
  claude/index.ts
  opencode/index.ts
  cursor/index.ts
  status-bar/index.ts # композиция индикаторов для workspace

server/modules/agents-integration/
  _/                 # объединение запросов и кеширование
  codex/index.ts     # получение лимитов через CLI
  claude/index.ts
  opencode/index.ts
  cursor/index.ts

core/modules/agents-integration/
  codex/index.ts     # browser-compatible контракты
  claude/index.ts
  opencode/index.ts
  cursor/index.ts
```

Отдельного модуля «integrations» нет: каждый сервис живёт в своём модуле. `integration-store` хранит `integrations.json` и секреты (его используют все сервисы); `github` и `gitlab` содержат API, авторизацию и импорт хоста; `docker` отдаёт собственный статус; `git-import` — общее ядро клонирования (защищённый HTTPS `git clone` через временный askpass, сценарий импорта и фоновые задачи), без знания о хостах. Страница настроек собирает статусы в маршруте `/api/integrations`. На клиенте то же разделение: `integration-api` (запросы и «глазок» токена), `github`, `gitlab`.

Ядро `_` доступно только адаптерам своего контейнера в своём корне; публичный `index.ts` ему не требуется. Серверные и клиентские адаптеры получают контракты из публичных подмодулей `core`, а не из чужого `_`. Контейнеры не образуют общего модуля между приложениями: матрица межкорневых зависимостей и запрет Node-инфраструктуры в браузере сохраняются. Каждый адаптер и приватное ядро имеют отдельный узел графа, поэтому циклы между ними проверяются.

Workspace подключает `AgentUsageIndicators` из `agents-integration/status-bar/index.ts`. Приватное ядро клиента управляет polling и рисует шкалу, а адаптеры определяют окна, подписи и IDE-команды. Серверное ядро объединяет одновременные запросы и хранит результат в переданном адаптером HMR-устойчивом состоянии. Парсеры, авторизация и сроки кеша принадлежат адаптерам: Claude сохраняет пятиминутный интервал, backoff и `Retry-After`; остальные используют минутный кеш. HTTP-адреса `/api/{codex,claude,opencode,cursor}/usage` и ID существующих IDE-команд сохранены.

`core` не зависит от приложений. Клиент использует только browser-compatible модули `core`; Node-модули `app-paths` и `os` недоступны браузеру и доменным модулям `core`. Сервер использует публичные модули `core`; GUI запускается в отдельном процессе через `native/app/entry.ts`. Native использует `core`, не импортируя серверную бизнес-логику. `vio` не зависит от Projector; его package exports (`vio`, `vio/core`, `vio/compiler`, `vio/register`) сохранены.

Модель проекта (`project`: тип, store, клиент API, маршрут) отделена от UI каталога (`catalog`: карточка, форма, настройки). Агент, раннер и интеграции зависят от лёгкого `project`, а не от компонентов. Каталог проектов и агент независимы в одну сторону: агент обновляет каталог. Настройки интерфейса на сервере принадлежат `preferences`; управление окнами не зависит от поиска launcher. Это устраняет циклы каталог/агент и launcher/window/processes.

## Вкладки и разделы workspace

Workspace не знает конкретных видов служебных вкладок и разделов сайдбара: их регистрируют владельцы, по образцу реестра команд (см. [SDK команд](ide-commands.md)).

- **Тип вкладки** (`TabType`, `workspace-api/tabs.ts`): `id`, `key(params)`, `path`, `title`, необязательные `hint`, `subtitle`, `read` (что видит агент) и `command` (IDE-команда открытия). Тип регистрирует профиль (`profile.tabs`) или базовый набор workspace (`lib/virtual-tabs.ts`). Открытие идёт по id: `openTab(id, params)`; одинаковый ключ только фокусирует вкладку, а сессия хранит `id` и `params` и пропускает неизвестные профилю типы.
- **Вид вкладки** (`TabView`, `lib/tab-views.ts`): компонент, `props(tab, host)` со слушателями событий, `keepAlive` (содержимое со состоянием остаётся смонтированным при переносе между блоками), `scroll`, `ownKeys` (горячие клавиши редактора не срабатывают внутри). Базовые виды лежат в `baseTabViews`, виды страницы приходят пропом `tabViews` у `ProjectWorkspace`. Что нужно виду от workspace, он берёт у `TabHost`.
- **Поведение** (`TabBehavior`: `dirty`, `beforeClose`, `save`) подключает владелец состояния через `useWorkspaceTabTypes`, например страница с формой настроек проекта.
- **Раздел сайдбара** (`SidebarType`, `workspace-api/sidebar.ts`) и **его вид** (`SidebarView`, `lib/sidebar-views.ts`) устроены так же: профиль добавляет разделы через `profile.sidebar` (`issues` — GitHub, `docker` — локальный проект), базовые `files`, `search`, `git` зависят от возможностей профиля (`requires`). Раздел сам решает, как обновляться (`refresh`) и что делать при выборе (`activate`).

Добавляя вид вкладки или раздел, не вносите условия по его имени в общий код: расширяйте контракт реестра.

## Размер файлов

Файл свыше 400 строк (для `.vue` — 500) должен быть в реестре `extra.largeFiles` файла `feod.config.mjs` с потолком и планом разбиения. Правило `large-files` падает, если файл вырос выше потолка, сократился (потолок нужно снизить), вернулся в порог (запись удалить) или исчез из репозитория. Список файлов и планов — в [large-files.md](large-files.md).

## Dock и workspace

Раскладка блоков редактора и терминалов принадлежит модулю `dock`: он знает только о панелях и вкладках, а их содержимое задают потребители. Модуль `workspace` делится на подмодули в `workspace/modules`: `git` (панель изменений, история, ветки; состояние в `git/lib/git-overview.ts`, `git/lib/git-history.ts`), `viewers` (CodeMirror, Markdown, SVG, HTML, изображения, архивы, обзор коммита, карточки issues/PR/discussions), `issues` (панели Issues, Pull requests, Discussions) и `tree` (дерево файлов). Подмодули независимы друг от друга и не зависят от значений родителя, поэтому общие запросы вынесены в модуль `workspace-api`, а форматирование времени — в `common`. Сам `workspace` собирает их: вкладки и открытые файлы (`lib/open-files.ts`, `lib/preview-tabs.ts`), раскладку блоков, поиск, сайдбар и панель инструментов. Раскладка графа Git — чистая функция `core/modules/workspace/git-graph.ts`.

## Профили workspace

Режимы workspace подключаются через `src/modules/workspace-api` как **профили**. `WorkspaceProfile` — единственный источник решений: набор провайдеров данных (`files` с необязательной записью, `git`, `search`), явные `features` (терминалы, Docker, агент, настройки, сохранение UI-состояния, внешние файлы) и пресет раскладки. `WorkspaceCapabilities` выводятся из профиля: `write` — из наличия `files.write`, `git`/`search` — из наличия провайдера. Функциональность спрашивает только профиль, а команды объявляют `requires: <capability>`; сравнений по идентификатору проекта, схеме или имени команды нет.

`createWorkspaceProfiles` — заменяемый корень композиции: резолверы по идентификатору проекта (первый подходящий), локальный профиль как запасной и регистрация готового профиля смонтированным представлением. Локальный профиль — HTTP backend Projector. GitHub (`github-workspace`) публикует профиль без записи: `files`, история Git, разделы Issues, Pull requests и Discussions, раскладка `editor`; терминалов, Docker и агента нет. Новый режим (контейнер, volume) добавляется профилем и провайдерами, без правок вкладок, дерева, тулбара и сайдбара. Строка `gh:/…` разбирается только в `ProjectRef` (`core/modules/project`).

## Разделы настроек

`app-settings/sections.ts` собирает разделы через контракт `SettingsSection` модуля `settings`: `id`, `title`, `group`, `description`, `keywords`, `component` и необязательные `props`. Для добавления раздела достаточно вклада в этот список; общий `SettingsWorkbench` не импортирует владельцев форм. Поиск учитывает названия, описания и ключевые слова параметров. Отдельная страница `/settings` хранит выбор в URL `?section=<id>`, а вкладка — в текущем состоянии формы; формы монтируются при первом открытии и сохраняют черновики при переключении до ухода со страницы. На узком экране навигация становится горизонтальной и прокручивается к выбранному разделу.

Воркспейсы подключают `settingsTabViews` через существующий контракт `TabViews`. Команда `ide.workbench.settings.open` открывает единственную вкладку `settings:app` в текущем воркспейсе; она сохраняет формы при переключении файлов и переносе между блоками. Настройки адаптируются к ширине самого блока, включая разделённые панели. Тип вкладки сохраняется существующей серверной сессией.

Команды `ide.settings.sections.list`, `ide.settings.section.open` (`{ id }`) и `ide.settings.search` (`{ query? }`) доступны в scope `settings`. Сохранение параметров принадлежит существующим формам и их серверным API.

## Проверка границ

Политика лежит в `feod.config.mjs` и исполняется плагином `@o-feod/oxlint-structure-plugin`: корни, зависимости между приложениями, `transitModules`, aliases, `parent-only` для подмодулей, публичные `index.ts`, запрет вычисляемых и неразрешённых импортов, циклы модулей (включая type-only, кроме импорта предка) и реестр размеров (`extra.largeFiles`). Платформенные ограничения заданы через `extra.confine`: `node:*`, `node-gtk`, `dbus-next`, `node-pty`, `ws` и модули `os`/`app-paths` разрешены только в `core/modules/os` и `core/modules/app-paths`, строки Linux и Windows — только в своих адаптерах. Это текстовая эвристика: значения, собранные во время выполнения, она не видит. Импорт `os`/`app-paths` ограничен для алиасов `@core/os` и `@core/app-paths`; относительные пути в обход алиаса не проверяются. Файлы вне корней (`tests`, `scripts`, `docs`) исключены через `ignore`.

Проверка обязательна в `vp run build`, `vp run test`, `vp run check` (`scripts/check-feod.mjs` запускает только правила FEOD через Oxlint). `vp build` выполняет её блокирующе и падает при нарушении. `vp dev` запускает её рядом с сервером (`checkFeodAsync`, таймаут 60 с) на каждом старте и перезапуске: нарушение или сбой Oxlint попадают в лог, а сервер продолжает работать; в каждом HMR-изменении проверка не выполняется. Её же показывает `vp lint` в виде диагностик по файлам. Отдельный запуск — `vp run architecture`; проверки политики на fixture-проектах — `vp run test:architecture`. Для полного набора проверок используйте `vp run check`.

Подмодуль может импортировать типы родителя без ложного цикла parent → child → parent (`childImportsParent`); зависимости значений и циклы между модулями проверяются.

Тесты могут обращаться к приватной реализации для проверки её поведения. В частности, HMR-тесты повторно импортируют implementation-файлы с query suffix: повторный импорт одного barrel не проверял бы перезагрузку реализации. Production-код не имеет таких исключений.

## Системный адаптер

`core/modules/os/index.ts` — единый Node API для CLI, сервера и native. Подмодули `os/modules/linux` и `os/modules/windows` приватны; внешние потребители не импортируют их напрямую. Linux содержит `/proc`, X11, KDE/D-Bus и GIO; Windows — процессы Win32, Credential Manager, меню Пуск и окно Chromium. GTK-renderer `vio` остаётся Linux-поверхностью. [Контракт адаптера](os.md).
