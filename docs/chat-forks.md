# Форки чатов в новые ветки

Изучение и реализация: ответвить разговор от выбранного сообщения в отдельный чат (новую
вкладку/ветку), не трогая исходный, и не потерять ветку после закрытия её вкладки. Решение прошлой
карты «отдельные чаты „отсюда“ не нужны» (`docs/agent-roadmap.md`, «Что не делаем») относилось к
временам, когда история чата была линейным JSON. Сейчас она дерево в SQLite, поэтому цена форка
другая.

**Статус:** v1 реализован — форк в новую вкладку и индекс чатов проекта. Что осталось — в конце.

## Короткий ответ

Форк — **новый чат-вкладка**: префикс ходов копируется в историю под новым ключом, вкладка
открывается с этим `chatId`. Исходный чат не меняется, обе ветки живут одновременно. Ключ истории —
произвольная строка, `PUT /api/agent/history/<key>` принимает любые ходы, а вкладка
`ide.workbench.<agent>.open` открывается с готовым `chatId`
(`src/modules/workspace-api/local.ts`, `src/modules/workspace/lib/editor-commands.ts`).

Сохранённый чат попадает в индекс проекта (`chat_index`), поэтому закрытая вкладка — обычного чата
или ветки — находится в «Недавних чатах» и открывается снова.

Ограничения честно:

- **Файлы не форкаются.** Снимков проекта по сообщениям нет (осознанное решение — откат файлов
  есть только у Claude Code). Форк — это ветка **разговора**, файлы остаются текущими. Настоящий
  «форк проекта на том шаге» потребует новой подсистемы снимков.
- **У ACP-агентов (Codex, OpenCode, Cursor, Kimi) ветка контекста беднее.** У них нет нативного
  форка: новый чат начинает новую сессию и переигрывает историю текстом — только последние 10 ходов,
  без результатов инструментов (`server/modules/agent/agent-host.ts`,
  `src/modules/agent/model/session.ts`).
- **Claude Code — лучший случай:** ветка создаётся нативной `forkSession(upToMessageId)` лениво, на
  первом сообщении форка (`server/modules/agents/claude-code/claude-code-checkpoints.ts:25`).
- **Штатный агент Projector** переигрывает префикс целиком (до ~90 тыс. знаков) вместе с вызовами
  инструментов, так что форк для него полноценный.

## Что уже есть в коде

| Механизм                                        | Где                                                                              | Что даёт форку                                                                                   |
| ----------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Дерево ходов в SQLite (`parent`, `pick`, `ord`) | `server/modules/agent/history-store.ts`                                          | Ветка — это просто другой набор строк; копирование префикса не ломает исходный чат               |
| Версии разговора (`variants`, `slot`)           | `src/modules/agent/model/branches.ts`                                            | Внутричатовые ветки уже есть (правка/повтор), но они **режут** текущий чат                       |
| Ключ чата на вкладку                            | `src/modules/agent/model/session.ts`                                             | `projector:<проект>:<chatId>` (или `<backend>:<проект>:<chatId>`) — отдельная история на вкладку |
| Команда вкладки чата                            | `src/modules/agent/lib/chat-tab.ts`                                              | По ключу чата даёт `{ command, args: { chatId } }`                                               |
| Параметры вкладок переживают перезагрузку       | `src/modules/workspace/lib/workspace-session.ts`                                 | Форк не теряется при reload, пока вкладка открыта                                                |
| `tail` + `sessionId` на ответе                  | `src/modules/agent/model/session.ts`                                             | Продолжение нативной сессии с нужной точки                                                       |
| `detached`                                      | `src/modules/agent/model/session.ts`, `server/modules/agents/acp/acp-backend.ts` | Принудительный новый нативный сеанс с переигрыванием истории                                     |
| `worktree` на ходе                              | `server/modules/agent/worktrees.ts`                                              | Форк может остаться в той же изолированной копии (см. риски)                                     |

Важно: форк в новую вкладку **не отменяет** версии. Версии — «переключиться на другую линию в том
же чате», форк — «оставить обе линии живыми одновременно». Это разные сценарии, и они не конфликтуют.

## Что значит «после сообщения»

Одна кнопка «форк» с неоднозначной точкой реза даёт плохие результаты, поэтому нужны две операции:

1. **«Ответвить до сообщения»** — для сообщения пользователя. В новый чат идут ходы **строго до**
   него, а его текст и чипы попадают **в поле ввода** нового чата. Пользователь меняет вопрос или
   отправляет как есть; оригинал остаётся нетронутым.
2. **«Продолжить в новом чате»** — для ответа агента (и, при желании, для пары «вопрос + ответ»).
   В новый чат идут ходы **включая** выбранный ответ; поле ввода пустое, следующее сообщение просто
   продолжает ветку.

Почему не «включить вопрос без ответа»: тогда префикс заканчивается ходом пользователя. У Claude
Code нативная ветка строится от `tail` предыдущего ответа, и висящий вопрос в неё не попадёт —
первое сообщение форка потеряет его из контекста. У ACP переигрывание истории тоже начинается с
нового сообщения, а ход-вопрос останется только в интерфейсе. Поэтому «до сообщения» всегда
выносит текст в черновик, а не оставляет висеть в истории.

Правило выбора режима: по умолчанию для хода пользователя — `before`, для ответа — `after`.

## Варианты реализации

### A. Новый чат-вкладка (рекомендуется)

Префикс ходов пишется в историю нового ключа, вкладка открывается командой чата.

- Плюсы: исходный чат не меняется; обе ветки живут одновременно; работает для всех бэкендов;
  вкладки уже персистентны; форк виден в `ide.agent.chats.list`; серверная часть — только индекс
  чатов, сам форк пишется обычным `PUT` истории.
- Минусы: плодит вкладки (опасение из прошлой карты); заголовок вкладки приходится передавать
  отдельно (параметр `title`), иначе все ветки назывались бы «Агент».
- Объём: ~1 день на штатного агента и Claude Code, +0,5–1 день на аккуратность с ACP и подписями.

### B. Именованные ветки внутри одного чата

Дерево в SQLite уже позволяет хранить ветки; нужен API, отдающий дерево, и UI дерева/списка веток,
плюс таблица имён веток. По сути это надстройка над `variants`.

- Плюсы: без новых вкладок; в одном месте видна вся история исследования.
- Минусы: самый большой UI; «создать ветку» без сообщения бессмысленна (ветка — это ход
  пользователя), значит, всё равно нужен ввод; переключение ветки режет показ (как сейчас).
- Вывод: это отдельная задача «просмотр дерева разговора», а не форк. Для запроса не нужна.

### C. Форк через архив истории

Архивировать текущий чат и сделать форк живым (`archiveLiveChat`/`openArchivedChat`,
`server/modules/agent/chat-archive.ts`).

- Плюс: форк сразу попадает в «Историю чатов».
- Минус: живой чат при этом **уезжает** в архив, то есть это перенос, а не параллельная ветка.
  Не подходит.

Рекомендация: **A**. При желании позже добавить к A «ссылку на родителя» (откуда форкнули) — колонка
`chats.fork` с `{ chat, turn }` или параметр вкладки; это даст навигацию между ветками без UI дерева.

## Как форк ложится на бэкенды

**Projector (штатный агент).** Нативной сессии нет: каждый запрос несёт историю
(`chatHistory(turns, true)` — с инструментами). Форк = копия префикса, дальше всё работает само.
Ограничение — бюджет `recentTurns` (~90 тыс. знаков, старые ходы отбрасываются).

**Claude Code.** В префиксе остаются `session` и `tail`. Первое сообщение форка вызовет
`sessionAt(cwd, session, tail)`; если нативный транскрипт уже ушёл дальше `tail` (а после любого
сообщения в исходном чате он уйдёт), будет создана ветка `forkSession(upToMessageId: tail)`. Старая
сессия остаётся нетронутой. Работает без правок сервера, но есть два нюанса:

- если форк сделали **с конца** разговора и исходный чат больше не используется, первое сообщение
  форка допишется в ту же нативную сессию (не ошибка: как только исходный чат напишет что-то ещё,
  он сам ответвится от `tail`). Если хочется гарантированно отдельный транскрипт — добавить в
  запрос флаг `fork: true` и в `sessionAt` всегда идти через `forkSession`;
- `rewind-files` в форке ссылается на `messageId` из общей/форкнутой сессии. Нужно проверить на
  живом Claude Code, сохраняются ли UUID при `forkSession`; если нет — откат файлов в форке
  отключить (кнопка «Откатить» остаётся только в исходном чате).

**ACP (Codex, OpenCode, Cursor, Kimi).** Обязательно помечать последний скопированный ответ
`detached: true`, иначе первый запрос форка сделает `session/load` **той же** нативной сессии
(`server/modules/agents/acp/acp-backend.ts`): агент увидит чужие ходы, а в интерфейсе форка их не
будет — расхождение контекста. С `detached` создаётся `session/new`, а префикс уходит
`promptWithHistory`: только 10 последних ходов и без tool-результатов. Это приемлемо для «ответвить и
продолжить», но не для «продолжить длинное исследование с полным контекстом».

**Изолированная копия (worktree).** Если исходный чат работал в копии, скопированный `worktree`
заставит форк работать **в той же** копии. Это удобно (общий песочный ящик), но после
merge/discard из любой ветки вторая получит «Изолированная копия уже удалена»
(`server/modules/agent/worktrees.ts`). Для v1: разрешить с предупреждением в описании команды и
панели; позже — опция `worktree: "same" | "new"` (новая копия от HEAD, с `detached`, потому что
нативную сессию в новую копию не перенести).

## Что происходит при закрытии вкладки

Данные форка **не удаляются**. До v1 терялся только путь к ним; теперь закрытый чат остаётся в
индексе проекта и открывается из «Недавних чатов» — но полезно знать, как это устроено:

- ходы пишутся в SQLite под ключом чата при каждом сохранении (`server/modules/agent/history-store.ts`);
  `deleteHistory` вызывается только из `deleteChat`/`removeArchivedChat`
  (`server/routes/api/agent-chats.ts`), закрытие вкладки его не вызывает;
- закрытие вкладки — это только удаление из массива вкладок
  (`src/modules/workspace/lib/open-files.ts`): `beforeClose` у чата нет, история не трогается;
- `chatId` живёт в параметрах вкладки, а снимок вкладок лежит в `sessionStorage`
  (`src/modules/workspace/lib/workspace-session.ts`, `src/common/utilities/session-snapshot.ts`).
  Перезагрузка страницы вкладку восстановит, закрытие — нет; ключ и заголовок остаются в `chat_index`;
- старый способ найти чат — только архивы **этого** ключа (`GET /api/agent/chats?key=`,
  `server/modules/agent/chat-archive.ts`) или CLI-сессии внешнего агента.

То есть после закрытия чат лежит в `~/.local/share/projector/agent/history.sqlite` под ключом
`projector:<проект>:<chatId>` (или `<backend>:<проект>:<chatId>`) и с v1 виден в списке проекта.
Записи, созданные до появления индекса, в него не попадают, но и не удаляются — доступны только
прямым запросом `GET /api/agent/history/<key>`, если ключ известен. Очистки таких «осиротевших»
ключей нет.

Это не свойство именно форков: любой дополнительный чат (`ide.workbench.agent.open` без `chatId`,
`create: () => ({ chatId: newId() })` в `src/modules/workspace-api/local.ts`) так же терял путь к
себе; индекс лечит это для всех. Частный случай — внешние агенты: сам разговор хранится в
транскрипте CLI и доступен через «Историю сессий» (`ide.agent.sessions.list` → `resumeSession`),
поэтому содержимое чата восстановимо и без индекса, но локальные версии/группировка — нет.

### Индекс чатов проекта — сделано

`chat_index` (таблица в `agent/history.sqlite`) хранит для каждого непустого чата проект, бэкенд,
заголовок из первого сообщения и время сохранения; пишется в той же транзакции, что и ходы
(`server/modules/agent/history-store.ts`). Пустой чат из списка удаляется. Архив при
`archiveLiveChat` запоминает проект и бэкенд в строке `archives`, и `openArchivedChat` возвращает
запись в индекс.

- `GET /api/agent/chats/recent?projectId=&backend=` — чаты проекта, новые первыми;
- `ide.agent.chats.recent` — то же для штатного агента;
- панель «История чатов» показывает блок «Недавние чаты»; клик открывает вкладку
  (`ide.workbench.<agent>.open { chatId, title }`) или фокусирует уже открытую.

Что этим **не** закрыто: удаления записи из списка (и очистки её истории) пока нет — список только
читается. Осиротевшие ключи от старых версий в индекс не попадают, но и не удаляются.

## Что сделано в v1 (вариант A)

1. **Рез разговора** — `forkAt(turns, turnId, mode)` в `model/branches.ts`: глубокое клонирование,
   снятие `run`, `variants`/`slot`, задачи `running` → `stopped` с пометкой.
2. **Ключ чата** — `model/chat-key.ts`; `useAgent` и форк считают его одинаково.
3. **Запись форка** — `model/chat-fork.ts`: `PUT` префикса в `/api/agent/history/<newKey>` с
   `projectId`/`backend` (сразу попадает в индекс), для внешних без `branchSession` — `detached` у
   последнего ответа, черновик — в `model/drafts.ts`, его забирает `useAgent` при создании состояния.
   Заголовок вкладки — «Ветка · <первая строка сообщения>».
4. **Действия чата** — `model/chat-branch.ts` (`useChatBranch`): форк, открытие недавнего чата,
   список для панели; `ChatController.fork` в `model/chat-registry.ts`.
5. **UI** — `AgentTurn.vue`: «Ответвить в новый чат» у сообщения пользователя (режим `before`) и
   «Продолжить в новом чате» в подвале ответа (`after`); `AgentSessions.vue` — блок «Недавние чаты».
6. **Команды** — `ide.agent.chat.fork { turnId, mode?, chat? }` и `ide.agent.chats.recent` в
   `model/branch-commands.ts`.
7. **Заголовок вкладки** — необязательный параметр `title` у вкладок агентов
   (`src/modules/workspace-api/local.ts`), чтобы ветки различались в полосе вкладок.
8. **Мелочи для размера файлов** — `model/chat-view.ts`, `model/chat-readout.ts`,
   `model/register-command.ts`; `lib/export.ts` (`downloadChatMarkdown`), `lib/plan.ts` (`shownPlan`).

Не вошло в v1: `fork: true` для Claude Code (ветка и так корректна: если транскрипт ушёл дальше
`tail`, `sessionAt` форкает сама; при форке с конца общая сессия дописывается, а исходный чат при
следующем сообщении ответвляется от своего `tail`), удаление записей индекса, отдельная нативная
копия для форка чата в worktree.

## Тесты

`tests/agent-fork.test.mjs`: `forkAt` для `before`/`after`, черновик с чипами, снятие
`run`/`variants`, остановка задач; `forkChat` с подставным `fetch` (ключ, тело запроса, `detached`

`agent-chats`, `agent-branches`, `agent-edit`, `agent-sessions` и проверки типов/архитектуры.

Что стоит проверить руками: форк из середины длинного чата, отправка в ветке, закрытие вкладки и
возврат через «Недавние чаты», форк чата Claude Code (нативная ветка) и ACP-чата (новый сеанс).
Браузерного автотеста на весь поток пока нет.

## Решения v1

1. Сделаны обе операции: `before` (вопрос уходит в поле ввода) и `after` (продолжение после ответа).
2. Форк чата в изолированной копии разрешён и работает в **той же** копии; описание команды
   предупреждает, что merge/discard затрагивает обе ветки.
3. Ссылка «откуда форкнули» заменена заголовком вкладки «Ветка · …»; связи между чатами в индексе нет.
4. Прежние версии в форк не переносятся — ветка чистая.
5. `fork: true` для Claude Code не делался (см. выше).
6. Индекс чатов проекта вошёл в v1.

## Дальше

- Черновик ветки `before` живёт в памяти до монтирования вкладки (как и любой набранный черновик, он
  не переживает перезагрузку страницы); текст при этом виден в заголовке вкладки «Ветка · …».
- Удаление чата из «Недавних» вместе с его историей (с подтверждением и запретом для открытой вкладки).
- Ссылка на родителя: `{ chat, turn }` в индексе и переход из ветки к исходному сообщению.
- Опция `worktree: "same" | "new"` для форка; сейчас копия общая.
- Браузерный тест потока «форк → вкладка → отправка → reload → возврат из списка».
