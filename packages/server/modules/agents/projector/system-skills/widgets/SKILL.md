# Создание виджетов Projector

Используй этот навык, когда нужно создать, изменить или исправить компонент в ответе агента: карточку, метрики, график, форму, кнопку или составной проектный виджет. Не путай их с панелями и вкладками workspace из `projector.browser`: для них действуют правила `docs/plugins.md`.

Перед работой прочитай `docs/agent-widgets.md` и ближайшие по смыслу определения в `packages/core/modules/agent-widgets`. Они описывают текущий контракт. Не выдумывай свойства по названию компонента.

## 1. Сначала выбери вид виджета

**Проектный виджет** создавай в `.projector/widgets.json`, если компонент нужен одному репозиторию и его можно собрать из существующих виджетов, HTML/SVG, CSS и небольшого скрипта. Сборка и изменение кода Projector не нужны. Это выбор по умолчанию для предметных карточек, отчётов, метрик и форм конкретного проекта.

**Встроенный виджет** добавляй в пакеты Projector только если он нужен всем проектам, требует собственной Vue-реализации или не выражается через проектный шаблон. Он требует синхронных изменений в `core`, `client`, `server`, регистрации имени и тестов.

Сначала проверь существующий каталог, не поддерживая в этой инструкции собственный список имён:

- Для виджетов текущего проекта вызови команду `ide.project.widgets.list`. Она возвращает определения из `.projector/widgets.json` без template/script/styles, путь к файлу, доверие и ошибку чтения.
- Для встроенных виджетов используй общие команды IDE: `list_commands` с query `ide.chat.widgets`, затем `describe_command` для выбранной команды и scope, затем `execute_command`. Каталог возвращает `ide.chat.widgets.list`, описание одного компонента — `ide.chat.widgets.describe` с args `{ "name": "GitInfo" }`; обе зарегистрированы в scope `workbench`. Отдельных tools `list_widgets`/`describe_widget` нет.
- Внешний агент вызывает те же команды через MCP `projector-ide`, когда возможность `ide` включена. Если команды IDE недоступны, не угадывай свойства специального виджета: используй обычный или попроси включить команды IDE.

Не создавай копию зарегистрированного компонента только ради другого текста или отступа. Композиция обычно лучше нового примитива. Не меняй `widget-runtime`, parser, compiler или doctors для обычного нового виджета.

## 2. Общий контракт хорошего виджета

- Имя — уникальный PascalCase-тег. Оно должно обозначать смысл, а не внешний вид: `BuildHealth`, а не `BlueCard`.
- `summary` объясняет агенту, **когда** использовать виджет и какие данные он показывает. Не описывай в нём файлы и внутреннюю реализацию.
- Для каждого prop укажи точный тип, понятное описание и `required: true`, если без значения компонент не имеет смысла. Не делай обязательными необязательные настройки оформления.
- `example` — минимальный полностью рабочий тег с реалистичными значениями. Он не должен ссылаться на необъявленные переменные или неизвестные компоненты.
- Используй только проверенные данные. Не помещай выдуманные показатели в пример реального ответа и не скрывай отсутствие данных нулём.
- Обычный часто используемый виджет описывай полностью. Для редкого сложного ставь `special: true`: в постоянной справке останутся имя и условие использования, а перед первым применением агент обязан вызвать `ide.chat.widgets.describe`.
- Не включай `special` просто ради сокращения файла: это увеличивает число шагов агента. Для встроенного виджета с большой матрицей props можно задать компактный `guide`, сохранив полные `props` и `notes` для подробного описания.
- `hidden: true` предназначен для legacy-виджетов, которые ещё рендерят старые ответы, но не должны предлагаться для новых. Не скрывай так новый компонент.

### Синтаксис разметки

Строки передавай обычным атрибутом, числа, boolean, массивы и объекты — через Vue-привязку:

```vue
<Stat label="Рост" value="12%" :delta="12" />
<Chips :items="['stable', { label: 'готово', tone: 'success' }]" mono />
```

Внутри виджета Markdown не обрабатывается. Вместо `**текста**`, списков `-`, `###` и Markdown-таблиц используй `<strong>`, `<ul><li>`, `<h3>` и `<table>`. Корневой тег закрывай явно или делай self-closing. В реальном ответе агента виджет пишется с новой строки прямо в сообщении, без fence ` ```vue `; fences нужны только в документации.

## 3. Проектный виджет `.projector/widgets.json`

### Базовая структура

```json
{
  "version": 1,
  "widgets": [
    {
      "name": "ModelMetrics",
      "summary": "метрики выбранной модели: скорость генерации и качество",
      "special": true,
      "props": {
        "model": {
          "type": "string",
          "description": "имя модели, для которой показываются метрики",
          "required": true
        }
      },
      "data": { "metrics": "reports/metrics.json" },
      "refresh": 30,
      "script": "const speed = computed(() => data.metrics?.speed ?? '—'); const quality = computed(() => data.metrics?.quality ?? '—'); return { speed, quality };",
      "styles": ".metrics { gap: 12px; } .note { color: var(--muted); }",
      "template": "<Card :title=\"model\"><Row class=\"metrics\"><Stat label=\"Скорость\" :value=\"speed\" /><Stat label=\"Качество\" :value=\"quality\" /></Row><p class=\"note\">Данные из отчёта проекта</p></Card>",
      "example": "<ModelMetrics model=\"gpt-5\" />"
    }
  ]
}
```

Для этого примера `reports/metrics.json` может содержать:

```json
{
  "speed": "42 ток/с",
  "quality": "8,7 / 10"
}
```

### Правила полей

- `name` обязателен: 2–40 символов, начинается с заглавной латинской буквы, далее только латинские буквы и цифры. Встроенные имена заняты. Дубликаты и рекурсивная ссылка виджета на самого себя не допускаются.
- `summary` обязателен, максимум 300 символов.
- `props` — объект до 24 свойств. У проектного виджета поддерживаются только `string`, `number`, `boolean`, `array`, `object` и объединения через `|`, например `string | number`. Описание каждого prop обязательно. Не переносите сюда TypeScript-интерфейсы, `enum` или сложные object shapes: они поддерживаются только как описательные типы во встроенных определениях.
- `template` обязателен, максимум 40 000 символов. Разрешены обычные HTML/SVG, встроенные виджеты и соседние проектные виджеты из того же файла, включая объявленные ниже. Произвольные PascalCase-компоненты, `<script>` и `<style>` внутри template запрещены.
- `script` — необязательное **тело функции**, максимум 20 000 символов. Это не содержимое `<script setup>`: не добавляй статические `import`/`export`. Заверши его `return { … }` со всеми значениями, которые нужны шаблону.
- `styles` — необязательный CSS до 20 000 символов. Селекторы автоматически ограничиваются обёрткой виджета. Поддерживаются `@media`, `@supports`, `@container`, `@layer`, `@keyframes` и `@font-face`; имена глобальных keyframes делай уникальными. Используй токены темы (`var(--text)`, `var(--muted)`, `var(--line)` и другие существующие), а не новую литеральную палитру.
- `data` — до восьми пар «имя → относительный путь к JSON». В template и script значения доступны как `data.<имя>`. Абсолютные пути, `..`, выход через symlink, специальные файлы, секретоподобные имена и файлы больше 1 МБ запрещены. Данные должны быть JSON, не JSONC.
- `refresh` — необязательный целый интервал перечитывания `data` от 5 до 3600 секунд. Не добавляй polling без потребности; в скрытой вкладке повторные чтения приостанавливаются.
- `notes` — до десяти коротких правил по 400 символов. Пиши только неочевидное поведение, которое нельзя понять из props.
- `example` желателен всегда, максимум 4000 символов. Если его опустить, получится только `<Имя />`, что плохо показывает обязательные props.
- `answer: true` разрешён только виджету, в template которого есть `IntelligentForm` или `Form`. Сам флаг не создаёт форму и не добавляет кнопку.

Нормализация может отбросить отдельные неверные props или data-записи, а невалидный виджет — целиком. Поэтому отсутствие ошибки парсинга JSON ещё не означает, что определение принято. Проверяй список в настройках проекта.

### Скрипт, props и данные

В `script` доступны `ref`, `reactive`, `computed`, `watch`, `onMounted`, `reply`, `props`, `data`, `dataErrors`, `dataLoading` и `dataError`.

```js
const multiplier = ref(2);
const total = computed(() => Number(props.amount ?? 0) * multiplier.value);
watch(
  () => props.amount,
  (value) => console.debug("amount changed", value),
);
return { multiplier, total };
```

- Скрипт запускается один раз для смонтированного экземпляра после первой загрузки объявленных данных. При последующих `refresh` реактивные `data` и computed обновляются без повторного запуска скрипта.
- В script ref читается через `.value`; в template Vue разворачивает его автоматически: `{{ total }}`, а не `{{ total.value }}`.
- `props`, `data`, `dataErrors`, `dataLoading` и `dataError` считай read-only. Для изменяемого состояния создавай собственные ref/reactive.
- Обрабатывай неполные данные через optional chaining и значения-пояснения. Не превращай отсутствие метрики в правдоподобный ноль без необходимости.
- Для `dataErrors` и `dataError` предусмотри понятное состояние ошибки. Не оставляй бесконечный пустой блок.
- Не создавай собственные глобальные timers, observers и listeners без необходимости: в project script не предоставлен `onBeforeUnmount`. Для периодического чтения файлов используй штатный `refresh`; реактивные effects и watchers останавливаются вместе со scope виджета. Если без ручного ресурса не обойтись, сначала проверь фактические возможности runtime и обеспечь cleanup, а не оставляй утечку.
- `reply(данные, "подпись")` отправляет сообщение агенту только после реального пользовательского действия. Не пытайся отправлять ответ из `onMounted`, `watch`, polling или программного `.click()`.

Не смешивай два механизма: `<script>` может встречаться внутри обычного Vue-блока в ответе агента, но **запрещён в `template` проектного виджета**. Для проектного виджета логика задаётся только отдельным JSON-полем `script`.

### Форма проекта

Для сбора нескольких параметров используй `IntelligentForm` и `Field` с уникальными `name`:

```json
{
  "name": "ReleaseOptions",
  "summary": "выбор канала выпуска и формирование release notes",
  "answer": true,
  "template": "<IntelligentForm summary=\"Параметры выпуска\"><Field type=\"radio\" name=\"channel\" label=\"Канал\" :options=\"['stable','beta']\" initial=\"stable\" required /><Field type=\"switch\" name=\"notes\" label=\"Сформировать release notes\" :initial=\"true\" /></IntelligentForm>",
  "example": "<ReleaseOptions />"
}
```

Не оборачивай такую форму в `Card` или `Form` и не добавляй `Button submit`: в композере отправляет общая кнопка, а в сообщении и readonly-снимке — собственная кнопка формы. Ответ агента должен заканчиваться `<ReleaseOptions />`, без текста после него. Не используй скрытые legacy `Input`, `Checks` и `Slider` в новой разметке: берите `Field` с нужным `type`.

Для новых полей выбирай `Field`: `text`, `textarea`, `number`, `slider`, `select`, `radio`, `checks`, `switch`, `date`, `time`, `segmented`. Обязательность проверяется до отправки. `checks` возвращает массив, `switch` — boolean, `number`/`slider` — number, остальные — string.

### Доверие и применение изменений

Проектный `script` — произвольный JavaScript на origin Projector, **не sandbox**. Он получает доступные странице браузерные API. `widgets.json` работает только после явного доверия пользователя к SHA-256 текущего содержимого.

- Не редактируй `agent/widget-trust.json`, не вычисляй хеш для обхода UI и не выдавай доверие самовольно. Попроси пользователя проверить файл и подтвердить доверие в **Настройки проекта → Виджеты проекта**.
- Любая правка `widgets.json`, включая template, script и styles, отзывает прежнее доверие. После изменения нужно повторное подтверждение.
- Не передавай токены и секреты через props, data, примеры или логи. Для показа уже существующего секрета используй штатный специальный сценарий `SafeSecretShow`, а не собственный обходной виджет.
- Правка влияет на новые и повторно открытые ответы; уже смонтированный ответ может сохранять прежнее определение до перезагрузки. MCP-процесс читает определения при старте сессии, поэтому для него может понадобиться новая сессия.
- Одинаковые имена в разных проектах не конфликтуют. Внутри одного файла имена должны быть уникальны.

## 4. Встроенный виджет Projector

Создавай его сквозным модулем, сохраняя FEOD-границы. Между пакетами импортируй через `@ai-projector/core/...`, внутри пакета — относительными путями и публичными `index.ts`.

### Шаг 1. Определение в core

Создай `packages/core/modules/agent-widgets/<имя>/index.ts`. Здесь не должно быть Vue или браузерного кода:

```ts
import { defineWidget } from "../../widget-catalog/index.ts";

export const gaugeWidget = defineWidget({
  name: "Gauge",
  group: "data",
  summary: "текущее значение показателя относительно заданного максимума",
  props: {
    label: { type: "string", description: "название показателя", required: true },
    value: { type: "number", description: "текущее значение", required: true },
    max: { type: "number", description: "положительный максимум шкалы", required: true },
    hint: { type: "string", description: "пояснение под показателем" },
  },
  example: '<Gauge label="Использовано" :value="42" :max="100" hint="условных единиц" />',
});
```

Доступные группы: `layout`, `data`, `form`, `action`, `project`. Для встроенного обычно используются первые четыре. При наличии `v-model` опиши `model`; для содержимого — `slot`; для неочевидных правил — `notes`. Не редактируй вручную собранный prompt: `widgetCatalog.guide()` и `ide.chat.widgets.describe` получают текст из определения.

Добавь имя в `BUILTIN_WIDGET_NAMES` в `packages/core/modules/widget-catalog/index.ts`. Без этого проектное имя не будет корректно зарезервировано, а контрактный тест упадёт.

### Шаг 2. Vue-реализация в client

Создай:

- `packages/client/modules/agent-widgets/<имя>/ui/<Имя>.vue`;
- `packages/client/modules/agent-widgets/<имя>/index.ts` с `WidgetEntry`.

```ts
import { gaugeWidget } from "@ai-projector/core/modules/agent-widgets/gauge/index.ts";
import type { WidgetEntry } from "../../widget-runtime/index.ts";
import Gauge from "./ui/Gauge.vue";

export const gauge: WidgetEntry = { definition: gaugeWidget, component: Gauge };
```

В `Gauge.vue` `defineProps` должен точно совпадать с определением по именам, типам и обязательности:

```vue
<script setup lang="ts">
const props = defineProps<{ label: string; value: number; max: number; hint?: string }>();
</script>

<template>
  <section :aria-label="props.label">
    <strong>{{ props.value }} / {{ props.max }}</strong>
    <p v-if="props.hint">{{ props.hint }}</p>
  </section>
</template>
```

Это скелет, а не готовый универсальный дизайн. В реальной реализации переиспользуй подходящий UI-kit из `packages/client/common/ui` (`UiStat`, `UiMeter`, `UiLineChart`, `UiField`, `UiButton` и другие), если он сокращает код. Не создавай общий UI-компонент ради одного потребителя.

Проверь:

- loading, empty, error, disabled и sent-состояния, если они применимы;
- нулевые, отрицательные, очень большие и неполные данные; не допускай `NaN`, деление на ноль и обещание несуществующего поведения;
- узкую ширину, переполнение длинным текстом и переносы;
- клавиатуру, фокус, native semantics, `aria-label` для icon-only и `alt` для изображений;
- тёмную, светлую и высококонтрастную темы через существующие токены;
- cleanup timers, observers, listeners и незавершённых запросов;
- стриминг: ввод, выбранная вкладка и DOM не должны сбрасываться при каждом чанке.

Если виджет выполняет действие продукта, используй зарегистрированную `ide.*` команду с понятными `title` и `description`, а не скрытый прямой вызов из кнопки. Если виджет отвечает агенту, используй штатный `Form`/`Button` или `reply` по пользовательскому действию.

### Шаг 3. Две регистрации

Добавь один и тот же виджет:

1. В `packages/client/app/widgets.ts` — `WidgetEntry` с Vue-компонентом.
2. В `packages/server/app/widgets.ts` — только определение из core для справки агента.

Клиент и сервер должны содержать одинаковый набор имён. Чат сам не импортирует встроенные виджеты. Не регистрируй серверную реализацию Vue и не добавляй определение в обход каталога.

### Шаг 4. Флаги справки и форм

- `special: true` — только редкому сложному виджету; summary должно точно сказать, когда вызвать `ide.chat.widgets.describe`.
- `guide` — компактная постоянная справка, но полные props остаются доступны в подробном описании.
- `answer: true` — только если блок действительно поддерживает сценарий следующего ответа, композер и readonly-снимок.
- `hidden: true` — только для совместимости со старыми ответами.

Постоянная встроенная справка ограничена 9500 символами. Не раздуй её полной документацией, дублированием примеров и перечислением очевидных props. Не удаляй полезные существующие описания только чтобы обойти бюджет: сначала используй `special` или продуманный `guide` для подходящих компонентов.

## 5. Проверки

### Для проектного виджета

1. Проверь JSON парсером и нормализацией проекта. Убедись, что виджет появился в настройках с нужными props, без тихо отброшенных полей.
2. Проверь связанные JSON-файлы: путь, размер, структуру, отсутствующие значения и ошибки чтения.
3. После содержательной проверки пользователь повторно доверяет текущий `widgets.json`. Обнови открытый чат/страницу, если действует ограничение старого смонтированного определения.
4. Попроси реального агента использовать `example`. Для `special` сначала проверь выдачу `ide.chat.widgets.describe`.
5. В реальном Chromium проверь первый рендер, streaming, данные, refresh, взаимодействия, ошибки консоли, узкую ширину и темы. Для формы — отправку, блокировку, readonly-снимок и повторное редактирование.
6. Не заявляй об успешном визуальном или интерактивном поведении, если browser/desktop был недоступен; прямо назови непроверенную часть.

Тесты контракта, когда менялись loader, validation, API или runtime:

```bash
vp test run packages/server/tests/project-widgets.test.mjs packages/server/tests/project-widgets-api.test.mjs
vp test run packages/client/tests/agent-widgets.test.mjs
vp test run packages/client/tests/agent-widgets-browser.test.mjs
```

Browser-тестам нужен Chromium. Не считай пропущенный browser-тест пройденной проверкой взаимодействия.

### Для встроенного виджета

```bash
vp test related packages/core/modules/agent-widgets/<имя>/index.ts packages/client/modules/agent-widgets/<имя>/index.ts
vp test run packages/client/tests/agent-widgets.test.mjs
vp test run packages/client/tests/agent-widgets-browser.test.mjs
vp check <изменённые файлы>
```

`agent-widgets.test.mjs` сверяет определения, `defineProps`, списки регистрации и бюджет справки. Browser-тест проверяет настоящий рендер и поведение; добавь в существующие тесты воспроизводимый риск нового компонента, не копируя реализацию в тест. Перед коммитом/PR выполни полный `vp run check`. Перед проверками работающего сервера смотри `/api/health` и `/api/status`; не завершай пользовательские терминалы полным restart без необходимости.

## 6. Критерий готовности

Работа завершена только когда:

- выбран правильный вид: проектный или встроенный, без дублирования существующего;
- имя, summary, props, notes и example согласованы с реальной реализацией;
- template валиден, внутри нет Markdown, запрещённых компонентов и `<script>`/`<style>` у проектного виджета;
- данные проверяемы, ошибки и пустые состояния понятны, секреты не раскрываются;
- формы используют `Field` и корректный сценарий последнего блока ответа;
- стили изолированы, используют темы и работают на узкой ширине;
- для встроенного заполнены `BUILTIN_WIDGET_NAMES` и обе регистрации;
- выполнены точечные тесты и реальная проверка пользовательского сценария, а ограничения среды явно названы;
- после изменения проектного файла пользователю ясно сказано о необходимости повторного доверия и, при необходимости, перезагрузки или новой MCP-сессии.
